## Початок роботи

### П: Що таке Azure Developer CLI (azd)?
**В**: Azure Developer CLI (azd) — це орієнтований на розробника інструмент командного рядка, який прискорює час, потрібний для того, щоб перенести ваш додаток з локального середовища розробки до Azure. Він забезпечує найкращі практики через шаблони та допомагає на всьому життєвому циклі розгортання.

### П: Чим azd відрізняється від Azure CLI?
**В**: 
- **Azure CLI**: універсальний інструмент для керування ресурсами Azure
- **azd**: інструмент, орієнтований на розробників для процесів розгортання додатків
- azd має власний процес автентифікації та розгортання; Azure CLI — окремий, додатковий інструмент
- azd включає шаблони, керування середовищами та автоматизацію розгортання

### П: Чи потрібно встановлювати Azure CLI для використання azd?
**В**: Для основного робочого процесу AZD — ні. Автентифікуйтеся за допомогою `azd auth login`. Встановлюйте Azure CLI окремо, коли шаблон або вправа явно виконують команди `az`.

### П: Які програмні мови підтримує azd?
**В**: azd не залежить від мови програмування. Працює з:
- Node.js/JavaScript/TypeScript
- Python
- .NET/C#
- Java
- Go
- PHP
- Сайтами зі статичним вмістом
- Контейнеризованими додатками

### П: Чи можу я використовувати azd із наявними проєктами?
**В**: Так! Ви можете:
1. Використати `azd init` для додавання конфігурації azd до наявних проєктів
2. Адаптувати наявні проєкти під структуру шаблонів azd
3. Створити власні шаблони на основі вашої існуючої архітектури

## Автентифікація та доступ

### П: Як автентифікуватися в Azure за допомогою azd?
**В**: Використовуйте `azd auth login`, який відкриє вікно браузера для автентифікації в Azure. Для сценаріїв CI/CD використовуйте службові принципали або керовані ідентичності.

### П: Чи можна використовувати azd з кількома підписками Azure?
**В**: Так. Використовуйте `azd env set AZURE_SUBSCRIPTION_ID <subscription-id>`, щоб вказати, яку підписку використовувати для кожного середовища.

### П: Які дозволи потрібні для розгортання з azd?
**В**: Зазвичай потрібні:
- Роль **Contributor** на групі ресурсів або підписці
- Роль **User Access Administrator**, якщо розгортаються ресурси, що потребують призначень ролей
- Конкретні дозволи варіюються залежно від шаблону та розгорнутих ресурсів

### П: Чи можна використовувати azd у CI/CD pipeline?
**В**: Безумовно! azd розроблений для інтеграції з CI/CD. Використовуйте службові принципали для автентифікації та встановлюйте змінні середовища для конфігурації.

### П: Як обробляти автентифікацію в GitHub Actions?
**В**: Віддавайте перевагу федерації ідентичностей для робочого навантаження (OIDC), налаштованій за допомогою `azd pipeline config`. Згенерований робочий процес встановлює AZD і автентифікує AZD безпосередньо з федеративною ідентичністю. Крок `azure/login` сам по собі не встановлює вхід у AZD. Крок входу всередині існуючої роботи виглядає так:
```yaml
permissions:
  contents: read
  id-token: write
steps:
  - uses: actions/checkout@v7
  - uses: Azure/setup-azd@v2
  - run: >-
      azd auth login
      --client-id "${{ vars.AZURE_CLIENT_ID }}"
      --tenant-id "${{ vars.AZURE_TENANT_ID }}"
      --federated-credential-provider github
```

Проводьте віртуальний або фактичний деплой після входу із правильно налаштованим середовищем AZD, підпискою та розташуванням. Федеративні облікові дані ідентичності повинні довіряти репозиторію/рефу робочого процесу або середовищу GitHub, а ролі Azure мають дозволяти потрібні операції.

## Шаблони та проєкти

### П: Де можна знайти шаблони azd?
**В**: 
- Офіційні та спільнотні шаблони: [Awesome AZD](https://azure.github.io/awesome-azd/)
- Шаблони спільноти: пошук GitHub за "azd-template"
- Використовуйте `azd template list` для перегляду наявних шаблонів

### П: Як створити власний шаблон?
**В**: 
1. Почніть з існуючої структури шаблону
2. Змініть `azure.yaml`, інфраструктурні файли та код додатку
3. Ретельно протестуйте за допомогою `azd up`
4. Опублікуйте на GitHub з відповідними тегами

### П: Чи можна використовувати azd без шаблону?
**В**: Так, використовуйте `azd init` у наявному проєкті, щоб створити необхідні конфігураційні файли. Вам потрібно буде вручну налаштувати `azure.yaml` та інфраструктурні файли.

### П: У чому різниця між офіційними та спільнотними шаблонами?
**В**: 
- **Офіційні шаблони**: підтримуються Microsoft, регулярно оновлюються, мають вичерпну документацію
- **Спільнотні шаблони**: створені розробниками, можуть мати спеціалізовані випадки використання, якість і підтримка можуть варіюватися

### П: Як оновити шаблон у своєму проєкті?
**В**: Шаблони не оновлюються автоматично. Ви можете:
1. Вручну порівняти і об’єднати зміни з джерельного шаблону
2. Почати з нуля за допомогою `azd init` з оновленим шаблоном
3. Вибірково застосувати конкретні покращення з оновлених шаблонів

## Розгортання та інфраструктура

### П: Які служби Azure можна розгортати за допомогою azd?
**В**: azd може розгортати будь-яку службу Azure за допомогою Bicep/ARM шаблонів, включно з:
- App Services, Container Apps, Functions
- Базами даних (SQL, PostgreSQL, Cosmos DB)
- Сховищами, Key Vault, Application Insights
- Мережевими, безпековими та моніторинговими ресурсами

### П: Чи можна розгортати в декілька регіонів?
**В**: Так, налаштуйте кілька регіонів у своїх Bicep шаблонах і встановіть параметр розташування відповідно для кожного середовища.

### П: Як керувати міграціями схеми бази даних?
**В**: Використовуйте хуки розгортання в `azure.yaml`:
```yaml
hooks:
  postdeploy:
    posix:
      run: ./scripts/migrate-database.sh
    windows:
      run: ./scripts/migrate-database.ps1
```

### П: Чи можна розгортати лише інфраструктуру без додатків?
**В**: Так, використовуйте `azd provision` для розгортання лише компонентів інфраструктури, визначених у ваших шаблонах.

### П: Як розгортати на існуючі ресурси Azure?
**В**: Так, якщо шаблон це підтримує. Посилайтеся на існуючі ресурси за допомогою декларацій `existing` Bicep або параметрів існуючих ресурсів, задокументованих у шаблоні, та мапуйте служби додатку до їх цільових ресурсів. Це не імпортує право власності і не створює автоматично відсутні дозволи. Перед розгортанням перегляньте шаблон.

### П: Чи можна використовувати Terraform замість Bicep?
**В**: Так. AZD підтримує Terraform на додаток до Bicep. Оберіть шаблон на базі Terraform або налаштуйте `infra.provider: terraform` у `azure.yaml` із відповідними файлами Terraform та конфігурацією стану/бекенду. Див. [робочий процес Terraform](https://learn.microsoft.com/azure/developer/azure-developer-cli/use-terraform-for-azd).

## Налаштування та середовища

### П: Як керувати різними середовищами (dev, staging, prod)?
**В**: Створюйте окремі середовища за допомогою `azd env new <environment-name>` і налаштовуйте різні параметри для кожного:
```bash
azd env new development
azd env new staging  
azd env new production
```

### П: Де зберігаються конфігурації середовищ?
**В**: У папці `.azure` у директорії вашого проєкту. Кожне середовище має власну папку з файлами конфігурації.

### П: Як встановити конфігурацію, специфічну для середовища?
**В**: Використовуйте `azd env set` для налаштування змінних середовища:
```bash
azd env set AZURE_LOCATION eastus
azd env set DATABASE_TIER Basic
```

### П: Чи можна ділитися конфігураціями середовищ між членами команди?
**В**: Папка `.azure` містить чутливу інформацію і не повинна комітитися в систему контролю версій. Натомість:
1. Документуйте необхідні змінні середовища
2. Використовуйте скрипти розгортання для налаштування середовищ
3. Використовуйте Azure Key Vault для чутливої конфігурації

### П: Як перевизначити стандартні налаштування шаблону?
**В**: Встановіть змінні середовища, що відповідають параметрам шаблону:
```bash
azd env set AZURE_LOCATION westus2
azd env set SKU_NAME "B1"
```

Лише змінні, що використовуються шаблоном, впливають на розгортання. `SKU_NAME` вище — приклад користувацького введення, а не універсальна настройка AZD.

## Усунення несправностей

### П: Чому `azd up` не вдається?
**В**: Типові причини:
1. **Проблеми автентифікації**: Запустіть `azd auth login`
2. **Недостатні дозволи**: Перевірте призначення ролей Azure
3. **Конфлікти імен ресурсів**: Перегляньте конфліктуючий ресурс і параметри іменування шаблону; створіть окреме середовище за допомогою `azd env new`, якщо потрібна ізоляція
4. **Проблеми з квотами/ємністю**: Перевірте регіональну доступність
5. **Помилки шаблону**: Перевірте Bicep шаблони

### П: Як налагоджувати помилки розгортання?
**В**: 
1. Використовуйте `azd deploy --debug` для докладного виводу
2. Перевірте історію розгортання в Azure порталі
3. Огляньте журнал активності в Azure порталі
4. Використовуйте `azd show` для відображення поточного стану середовища

### П: Чому мої змінні середовища не працюють?
**В**: Перевірте:
1. Імена змінних точно відповідають параметрам шаблону
2. Значення належно взяті в лапки, якщо містять пробіли
3. Обране середовище: `azd env select <environment>`
4. Змінні встановлені у правильному середовищі

### П: Як очистити хибні розгортання?
**В**: 
```bash
azd down
```
Спершу перегляньте вибране середовище та підтвердження видалення. Це видаляє створені ресурси Azure, а не локальну конфігурацію середовища `.azure`. `--purge` також запитує постійне видалення підтримуваних ресурсів із м’яким видаленням, і може блокуватися захистом зберігання/очищення; це не рутинний крок відновлення.

### П: Чому мій додаток недоступний після розгортання?
**В**: Перевірте:
1. Розгортання завершене успішно
2. Додаток працює (перевірте журнали в Azure порталі)
3. Мережеві групи безпеки дозволяють трафік
4. DNS/користувацькі домени налаштовані правильно

## Витрати та білінг

### П: Скільки коштуватиме розгортання azd?
**В**: Витрати залежать від:
- Розгорнутих служб Azure
- Обраних рівнів сервісу/SKU
- Регіональних відмінностей у цінах
- Шаблонів використання

Використовуйте [Калькулятор цін Azure](https://azure.microsoft.com/pricing/calculator/) для оцінок.

### П: Як контролювати витрати при розгортанні azd?
**В**: 
1. Використовуйте нижчі рівні SKU для середовищ розробки
2. Налаштуйте бюджети та сповіщення Azure
3. Використовуйте `azd down` для видалення ресурсів, коли вони не потрібні
4. Обирайте відповідні регіони (витрати різняться за розташуванням)
5. Використовуйте інструменти Azure Cost Management

### П: Чи є безкоштовні рівні для шаблонів azd?
**В**: Деякі служби мають безкоштовні SKU або щомісячні гранти, залежно від права на участь, плану хостингу, регіону та обмежень підписки. Вони не роблять повністю безкоштовним весь шаблон: бази даних, пошук, мережі, реєстри, телеметрія та виведення моделей можуть спричинити окремі витрати. Перед розгортанням перевіряйте [список безкоштовних служб Azure](https://azure.microsoft.com/free/) і актуальні ціни для кожного ресурсу.

### П: Як оцінити витрати перед розгортанням?
**В**: 
1. Перегляньте `main.bicep` шаблону, щоб побачити, які ресурси створюються
2. Використовуйте Azure Pricing Calculator із конкретними SKU
3. Спершу розгорніть у середовищі розробки для моніторингу реальних витрат
4. Скористайтеся Azure Cost Management для детального аналізу витрат

## Найкращі практики

### П: Які найкращі практики для структури проєкту azd?
**В**: 
1. Тримайте код додатку окремо від інфраструктури
2. Використовуйте змістовні імена служб у `azure.yaml`
3. Реалізуйте належну обробку помилок у скриптах збірки
4. Використовуйте конфігурації, специфічні для середовищ
5. Включайте вичерпну документацію

### П: Як організувати кілька служб в azd?
**В**: Використовуйте рекомендовану структуру:
```
├── src/
│   ├── web/          # Frontend service
│   ├── api/          # Backend service  
│   └── worker/       # Background service
├── infra/            # Infrastructure templates
├── azure.yaml        # azd configuration
└── README.md         # Project documentation
```

### П: Чи варто додавати папку `.azure` у систему контролю версій?
**В**: **Ні!** Папка `.azure` містить чутливу інформацію. Додайте її до `.gitignore`:
```gitignore
.azure/
```

### П: Як мені працювати з секретами та конфіденційними налаштуваннями?
**В**: 
1. Використовуйте Azure Key Vault для секретів
2. Посилайтеся на секрети Key Vault у конфігурації застосунку
3. Ніколи не комітьте секрети у систему контролю версій
4. Використовуйте керовані ідентичності для аутентифікації між сервісами

### П: Який рекомендований підхід для CI/CD з azd?
**В**: 
1. Використовуйте окремі середовища для кожного етапу (розробка/стейджинг/продакшн)
2. Реалізуйте автоматизоване тестування перед деплоєм
3. Використовуйте сервісні облікові записи для аутентифікації
4. Зберігайте конфіденційну конфігурацію у секретах/змінних конвеєра
5. Реалізуйте погоджувальні двері для розгортань у продакшн

## Розширені теми

### П: Чи можу я розширити azd користувацькою функціональністю?
**В**: Так, через хуки деплою у `azure.yaml`:
```yaml
hooks:
  predeploy:
    run: ./scripts/custom-setup.sh
  postdeploy:
    run: ./scripts/custom-config.sh
```

### П: Як інтегрувати azd із існуючими DevOps процесами?
**В**: 
1. Використовуйте команди azd у наявних скриптах конвеєра
2. Стандартизуйте шаблони azd у командах
3. Інтегруйте з теперішнім моніторингом та алертами
4. Використовуйте JSON-вивід azd для інтеграції в конвеєр

### П: Чи можу я використовувати azd з Azure DevOps?
**В**: Так, azd працює з будь-якою CI/CD системою. Створюйте Azure DevOps конвеєри, що використовують команди azd.

### П: Як я можу зробити внесок у azd або створювати шаблони спільноти?
**В**: 
1. **Інструмент azd**: Робіть внесок до [Azure/azure-dev](https://github.com/Azure/azure-dev)
2. **Шаблони**: Дотримуйтеся інструкцій внеску в галерею [Awesome AZD](https://github.com/Azure/awesome-azd#3-contribute-to-gallery)
3. **Документація**: Робіть внесок у документацію на [MicrosoftDocs/azure-dev-docs](https://github.com/MicrosoftDocs/azure-dev-docs)

### П: Які плани розвитку azd?
**В**: Перевірте [офіційний дорожню карту](https://github.com/Azure/azure-dev/projects) для запланованих функцій та покращень.

### П: Як мені мігрувати з інших інструментів деплою на azd?
**В**: 
1. Проаналізуйте поточну архітектуру деплою
2. Створіть еквівалентні Bicep шаблони
3. Налаштуйте `azure.yaml` відповідно до поточних сервісів
4. Ретельно протестуйте в середовищі розробки
5. Поступово мігруйте середовища
