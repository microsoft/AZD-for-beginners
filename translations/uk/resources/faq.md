## Початок роботи

### Питання: Що таке Azure Developer CLI (azd)?
**Відповідь**: Azure Developer CLI (azd) — це орієнтований на розробника інструмент командного рядка, який прискорює час від початку розробки застосунку локально до його розгортання в Azure. Він пропонує найкращі практики через шаблони та підтримує весь життєвий цикл розгортання.

### Питання: Чим azd відрізняється від Azure CLI?
**Відповідь**: 
- **Azure CLI**: універсальний інструмент для керування ресурсами Azure
- **azd**: інструмент, орієнтований на розробників для робочих процесів розгортання застосунків
- azd має власну автентифікацію та процес розгортання; Azure CLI — окремий, додатковий інструмент
- azd включає шаблони, управління середовищами та автоматизацію розгортання

### Питання: Чи потрібно встановлювати Azure CLI для використання azd?
**Відповідь**: Для основного робочого процесу AZD — ні. Для автентифікації використовуйте `azd auth login`. Встановлюйте Azure CLI окремо, якщо шаблон чи завдання явно використовують команди `az`.

### Питання: Які мови програмування підтримує azd?
**Відповідь**: azd не залежить від мови. Працює з:
- Node.js/JavaScript/TypeScript
- Python
- .NET/C#
- Java
- Go
- PHP
- Статичні вебсайти
- Контейнеризовані застосунки

### Питання: Чи можу я використовувати azd з існуючими проектами?
**Відповідь**: Так! Ви можете:
1. Використати `azd init` для додавання конфігурації azd в існуючі проекти
2. Адаптувати наявні проекти під структуру шаблону azd
3. Створювати власні шаблони на основі вашої існуючої архітектури

### Питання: Що змінилося із загальною доступністю розширення Foundry?
**Відповідь**: Пакет `microsoft.foundry` досяг версії 1.0 і GA 5 листопада 2026 року. В AZD 1.37.0+ використовуйте `azd ext install microsoft.foundry` для встановлення семи основних розширень для агентів, підключень, інспектора, проектів, рутин, навичок і наборів інструментів. Це не новий простір імен для команд, а компоненти мають окремі версії. Оцінки, набори даних, точне налаштування й власні моделі встановлюються окремо; функції попереднього перегляду не стають GA автоматично через GA пакета.

Посібник [hosted-agent walkthrough](../docs/chapter-02-ai-development/microsoft-foundry-integration.md#hosted-agent-walkthrough-ga) використовує Python 3.13+ та актуальну версію uv. `azd ai agent run` відкриває Agent Inspector локально, але виклики моделей і далі використовують Azure і мають плату. Режим коду `azd deploy` завантажує вихідний код для віддаленої збірки без потреби збирати локальний контейнер.

### Питання: Чи видаляє `azd down` розміщеного агента з існуючого проєкту Foundry?
**Відповідь**: Ні, якщо йдеться про шлях повторного використання проєкту, описаний у швидкому старті hosted-agent: агент, проект та інші ресурси залишаються. Видаляйте небажані ресурси окремо, не видаляючи спільні. Якщо середовище створило новий проєкт Foundry, `azd down` видаляє його ресурсну групу та все всередині. Перед підтвердженням ознайомтеся з [керівництвом з очищення](../docs/chapter-02-ai-development/microsoft-foundry-integration.md#7-clean-up-deliberately) і підказками видалення.

## Автентифікація та доступ

### Питання: Як автентифікуватися в Azure за допомогою azd?
**Відповідь**: Використовуйте `azd auth login`, що відкриє вікно браузера для автентифікації в Azure. Для CI/CD застосовуйте сервісні принципали або керовані ідентичності.

### Питання: Чи можна використовувати azd з кількома підписками Azure?
**Відповідь**: Так. Використовуйте `azd env set AZURE_SUBSCRIPTION_ID <subscription-id>` для вказівки підписки для кожного середовища.

### Питання: Які права потрібні для розгортання з azd?
**Відповідь**: Зазвичай потрібно:
- Роль **Contributor** на ресурсній групі або підписці
- Роль **User Access Administrator** при розгортанні ресурсів, що вимагають призначення ролей
- Конкретні права залежать від шаблону і розгорнутих ресурсів

### Питання: Чи можна використовувати azd у CI/CD конвеєрах?
**Відповідь**: Абсолютно! azd створений для інтеграції з CI/CD. Використовуйте сервісні принципали для автентифікації та встановлюйте змінні середовища для конфігурації.

### Питання: Як працювати з автентифікацією в GitHub Actions?
**Відповідь**: Надавайте перевагу федерації ідентичностей для робочого навантаження (OIDC), налаштованій через `azd pipeline config`. Згенерований робочий процес встановлює AZD і автентифікує AZD безпосередньо через федеративну ідентичність. Один крок `azure/login` не встановлює вхід в AZD. Крок входу в межах наявної роботи:
```yaml
permissions:
  contents: read
  id-token: write
steps:
  - uses: actions/checkout@v7
  - uses: Azure/setup-azd@v2
  - run: >-
      azd auth login
      --client-id "${{ vars.AZURE_CLIENT_ID }}"
      --tenant-id "${{ vars.AZURE_TENANT_ID }}"
      --federated-credential-provider github
```

Проводьте створення чи розгортання після входу з призначеним для AZD середовищем, підпискою та регіоном. Федеративні облікові дані ідентичності мають довіряти репозиторію/рефу робочого процесу або середовищу GitHub, а ролі Azure ідентичності мають дозволяти потрібні операції.

## Шаблони та проекти

### Питання: Де можна знайти шаблони azd?
**Відповідь**: 
- Офіційні та спільнотні шаблони: [Awesome AZD](https://azure.github.io/awesome-azd/)
- Спільнотні шаблони: пошук GitHub за "azd-template"
- Використовуйте `azd template list` для перегляду доступних шаблонів

### Питання: Як створити власний шаблон?
**Відповідь**: 
1. Почніть із існуючої структури шаблону
2. Змініть `azure.yaml`, інфраструктурні файли та код застосунку
3. Ретельно протестуйте за допомогою `azd up`
4. Опублікуйте на GitHub з відповідними тегами

### Питання: Чи можна використовувати azd без шаблону?
**Відповідь**: Так, використовуйте `azd init` у наявному проєкті для створення необхідних конфігураційних файлів. Вам знадобиться вручну налаштувати `azure.yaml` та інфраструктурні файли.

### Питання: У чому різниця між офіційними та спільнотними шаблонами?
**Відповідь**: 
- **Офіційні шаблони**: Підтримуються Microsoft, регулярно оновлюються, мають вичерпну документацію
- **Шаблони спільноти**: Створені розробниками, можуть мати спеціалізовані випадки використання, різна якість та підтримка

### Питання: Як оновити шаблон у моєму проєкті?
**Відповідь**: Шаблони не оновлюються автоматично. Ви можете:
1. Вручну порівняти та об’єднати зміни з оригінальним шаблоном
2. Почати наново з `azd init`, використовуючи оновлений шаблон
3. Вибірково застосувати окремі покращення з оновлених шаблонів

## Розгортання та інфраструктура

### Питання: Які служби Azure може розгортати azd?
**Відповідь**: azd може розгортати будь-яку службу Azure через шаблони Bicep/ARM, включно з:
- App Services, Container Apps, Functions
- Бази даних (SQL, PostgreSQL, Cosmos DB)
- Сховища, Key Vault, Application Insights
- Мережеві, безпекові та моніторингові ресурси

### Питання: Чи можна розгортати в кілька регіонів?
**Відповідь**: Так, налаштуйте кілька регіонів у ваших шаблонах Bicep і коректно встановіть параметр location для кожного середовища.

### Питання: Як виконувати міграції схем баз даних?
**Відповідь**: Використовуйте хуки розгортання у `azure.yaml`:
```yaml
hooks:
  postdeploy:
    posix:
      run: ./scripts/migrate-database.sh
    windows:
      run: ./scripts/migrate-database.ps1
```

### Питання: Чи можна розгортати лише інфраструктуру без застосунків?
**Відповідь**: Так, використовуйте `azd provision` для розгортання лише інфраструктурних компонентів, визначених у ваших шаблонах.

### Питання: Як розгортати на існуючі ресурси Azure?
**Відповідь**: Якщо шаблон це підтримує. Посилайтеся на існуючі ресурси за допомогою декларацій Bicep `existing` або параметрів шаблону для існуючих ресурсів, і зіставляйте сервіси застосунку із запланованими цілями. Це не імпортує права власності і не створює автоматично відсутні права. Перед розгортанням ознайомтесь із шаблоном.

### Питання: Чи можна замість Bicep використовувати Terraform?
**Відповідь**: Так. AZD підтримує Terraform і Bicep. Виберіть шаблон на основі Terraform або налаштуйте `infra.provider: terraform` у `azure.yaml` з відповідними файлами Terraform та конфігурацією стану/бекенду. Деталі — у [Terraform workflow](https://learn.microsoft.com/azure/developer/azure-developer-cli/use-terraform-for-azd).

## Конфігурація та середовища

### Питання: Як керувати різними середовищами (dev, staging, prod)?
**Відповідь**: Створюйте окремі середовища за допомогою `azd env new <environment-name>` і налаштовуйте для кожного різні параметри:
```bash
azd env new development
azd env new staging  
azd env new production
```

### Питання: Де зберігаються настройки середовищ?
**Відповідь**: У папці `.azure` всередині каталогу вашого проєкту. Кожне середовище має свою папку з файлами конфігурації.

### Питання: Як задавати конфігурацію для конкретного середовища?
**Відповідь**: Використовуйте `azd env set` для встановлення змінних середовища:
```bash
azd env set AZURE_LOCATION eastus
azd env set DATABASE_TIER Basic
```

### Питання: Чи можна ділитися конфігурацією середовищ між членами команди?
**Відповідь**: Папка `.azure` містить конфіденційну інформацію і її не слід додавати у систему контролю версій. Натомість:
1. Документуйте необхідні змінні середовища
2. Використовуйте скрипти розгортання для налаштування середовищ
3. Використовуйте Azure Key Vault для конфіденційної конфігурації

### Питання: Як перевизначати стандартні налаштування шаблону?
**Відповідь**: Задавайте змінні середовища, що відповідають параметрам шаблону:
```bash
azd env set AZURE_LOCATION westus2
azd env set SKU_NAME "B1"
```

Тільки змінні, які використовує шаблон, впливають на розгортання. `SKU_NAME` вище — приклад власного вхідного параметра, а не універсальна налаштування AZD.

## Усунення несправностей

### Питання: Чому не вдається `azd up`?
**Відповідь**: Найпоширеніші причини:
1. **Проблеми з автентифікацією**: Виконайте `azd auth login`
2. **Недостатні права**: Перевірте призначення ролей Azure
3. **Конфлікти назв ресурсів**: Перегляньте конфліктуючий ресурс і параметри іменування шаблону; створіть окреме середовище з `azd env new`, якщо потрібна ізоляція
4. **Проблеми з квотами/ємністю**: Перевірте доступність у регіоні
5. **Помилки в шаблонах**: Валідатор шаблонів Bicep

### Питання: Як налагоджувати помилки розгортання?
**Відповідь**: 
1. Використовуйте `azd deploy --debug` для детального виводу
2. Перевірте історію розгортань у порталі Azure
3. Ознайомтесь із журналом активності в порталі Azure
4. Використовуйте `azd show` для відображення поточного стану середовища

### Питання: Чому мої змінні середовища не працюють?
**Відповідь**: Перевірте:
1. Імена змінних точно збігаються з параметрами шаблону
2. Значення правильно взяті в лапки, якщо містять пробіли
3. Вибране правильне середовище: `azd env select <environment>`
4. Змінні встановлені у потрібному середовищі

### Питання: Як очистити невдалі розгортання?
**Відповідь**: 
```bash
azd down
```
Спочатку перегляньте вибране середовище і підтвердження видалення. Це видалить провізовані ресурси Azure, а не локальну конфігурацію середовища `.azure`. `--purge` додатково запитує постійне видалення підтримуваних м’яко видалених ресурсів і може бути заблокований політиками зберігання/очищення; це не рутинний крок відновлення.

### Питання: Чому після розгортання моє застосування недоступне?
**Відповідь**: Перевірте:
1. Розгортання завершилося успішно
2. Застосунок працює (перевірте журнали в порталі Azure)
3. Мережеві групи безпеки дозволяють трафік
4. DNS/власні домени налаштовані правильно

## Вартість і оплата

### Питання: Скільки коштуватиме розгортання azd?
**Відповідь**: Вартість залежить від:
- розгорнутих служб Azure
- обраних рівнів сервісів/SKU
- регіональних цінових відмінностей
- шаблонів використання

Використовуйте [Калькулятор цін Azure](https://azure.microsoft.com/pricing/calculator/) для оцінок.

### Питання: Як контролювати витрати в розгортаннях azd?
**Відповідь**: 
1. Використовуйте нижчі SKU для середовищ розробки
2. Встановлюйте бюджети та сповіщення Azure
3. Використовуйте `azd down` для видалення ресурсів, коли вони не потрібні
4. Обирайте відповідні регіони (вартість залежить від місця)
5. Використовуйте інструменти управління витратами Azure

### Питання: Чи є у azd шаблонах варіанти безкоштовного рівня?
**Відповідь**: Деякі сервіси мають безкоштовні SKU або щомісячні гранти, залежно від відповідності, плану хостингу, регіону та обмежень підписки. Це не робить весь шаблон безкоштовним: бази даних, пошук, мережі, реєстри, телеметрія та інференс моделей можуть викликати додаткові витрати. Перевірте [список безкоштовних сервісів Azure](https://azure.microsoft.com/free/) та актуальні ціни для кожного ресурсу перед розгортанням.

### Питання: Як оцінити вартість перед розгортанням?
**Відповідь**: 
1. Перегляньте `main.bicep` шаблону, щоб побачити, які ресурси створюються
2. Використовуйте Калькулятор цін Azure з конкретними SKU
3. Спочатку розгорніть у середовищі розробки для моніторингу фактичних витрат
4. Використовуйте Azure Cost Management для детального аналізу витрат

## Кращі практики

### Питання: Які кращі практики для структури проєкту azd?
**Відповідь**: 
1. Тримайте код застосунку окремо від інфраструктури
2. Використовуйте значущі імена сервісів в `azure.yaml`
3. Реалізуйте правильну обробку помилок у скриптах збірки
4. Використовуйте конфігурацію, специфічну для середовища
5. Включайте повну документацію

### Питання: Як організувати кілька сервісів в azd?
**Відповідь**: Використовуйте рекомендовану структуру:
```
├── src/
│   ├── web/          # Frontend service
│   ├── api/          # Backend service  
│   └── worker/       # Background service
├── infra/            # Infrastructure templates
├── azure.yaml        # azd configuration
└── README.md         # Project documentation
```

### Питання: Чи потрібно додавати папку `.azure` до системи контролю версій?
**Відповідь**: **Ні!** Папка `.azure` містить конфіденційну інформацію. Додайте її до `.gitignore`:
```gitignore
.azure/
```

### Питання: Як працювати з секретами і конфіденційною конфігурацією?
**Відповідь**: 
1. Використовуйте Azure Key Vault для зберігання секретів
2. Посилайтесь на секрети Key Vault у конфігурації застосунку
3. Ніколи не додавайте секрети до системи контролю версій
4. Використовуйте керовані ідентичності для аутентифікації між сервісами

### Питання: Який рекомендований підхід для CI/CD з azd?
**Відповідь**: 
1. Використовуйте окремі середовища для кожного етапу (розробка/тестування/продакшн)
2. Реалізуйте автоматизоване тестування перед розгортанням
3. Використовуйте service principals для аутентифікації
4. Зберігайте конфіденційну конфігурацію у секретах/змінних pipeline
5. Виконуйте контрольні точки затвердження для продакшн розгортань

## Розширені теми

### Питання: Чи можу я розширити azd користувацьким функціоналом?
**Відповідь**: Так, через deployment hooks у `azure.yaml`:
```yaml
hooks:
  predeploy:
    run: ./scripts/custom-setup.sh
  postdeploy:
    run: ./scripts/custom-config.sh
```

### Питання: Як інтегрувати azd з існуючими DevOps процесами?
**Відповідь**: 
1. Використовуйте azd команди у існуючих скриптах pipeline
2. Стандартизуйте шаблони azd між командами
3. Інтегруйте з існуючим моніторингом та сповіщеннями
4. Використовуйте JSON вивід azd для інтеграції в pipeline

### Питання: Чи можна використовувати azd з Azure DevOps?
**Відповідь**: Так, azd працює з будь-якою CI/CD системою. Створюйте Azure DevOps pipelines, які використовують azd команди.

### Питання: Як я можу зробити внесок у azd або створити спільнотні шаблони?
**Відповідь**: 
1. **azd tool**: Долучайтесь до [Azure/azure-dev](https://github.com/Azure/azure-dev)
2. **Шаблони**: Дотримуйтесь [інструкцій внеску у галерею Awesome AZD](https://github.com/Azure/awesome-azd#3-contribute-to-gallery)
3. **Документація**: Вносьте зміни до документів у [MicrosoftDocs/azure-dev-docs](https://github.com/MicrosoftDocs/azure-dev-docs)

### Питання: Які плани розвитку azd?
**Відповідь**: Перевірте [офіційну дорожню карту](https://github.com/Azure/azure-dev/projects) для планованих функцій та покращень.

### Питання: Як мігрувати з інших інструментів розгортання на azd?
**Відповідь**: 
1. Проаналізуйте поточну архітектуру розгортання
2. Створіть еквівалентні Bicep шаблони
3. Налаштуйте `azure.yaml` відповідно до поточних сервісів
4. Ретельно тестуйте у середовищі розробки
5. Поступово мігруйте середовища
