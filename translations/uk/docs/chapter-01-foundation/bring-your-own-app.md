# Принеси власний додаток — додайте azd до існуючого проєкту

**Навігація по розділах:**
- **📚 Головна курсу**: [AZD для початківців](../../README.md)
- **📖 Поточний розділ**: Розділ 1 — Основи та швидкий старт
- **⬅️ Попередній**: [Ваш перший проєкт](first-project.md)
- **➡️ Наступний**: [Dev Containers і Codespaces](dev-containers.md)

> Мета перевірки команд та конфігурації: `azd 1.37.2` (листопад 2026). Згенеровані файли залежать від виявленого додатка; розгортання в Azure не здійснювалося під час цього огляду.

## Вступ

У [Вашому першому проєкті](first-project.md) ви розгорнули додаток, починаючи з шаблону. Але найчастіше у вас вже *є* додаток — Node.js API, сервіс Python Flask, .NET веб-додаток — який знаходиться в папці на вашому комп’ютері. Цей урок показує, як додати azd до цього існуючого коду, щоб можна було розгорнути його за допомогою `azd up`, без необхідності шаблону.

## Навчальні цілі

Наприкінці цього уроку ви:
- Зрозумієте три способи початку проєкту azd
- Запустите `azd init` всередині існуючого коду
- Зрозумієте, що роблять `azure.yaml` та папка `infra/` для вашого додатку
- Дізнаєтесь, коли дозволити azd генерувати інфраструктуру, а коли писати її самому
- Розгорнете існуючий додаток в Azure за допомогою `azd up`

## Результати навчання

Після завершення уроку ви зможете:
- Ініціалізувати azd у проєкті, який у вас вже є
- Читати та редагувати базовий файл `azure.yaml`
- Генерувати початкову інфраструктуру за допомогою `azd infra generate`
- Обрати відповідний хост Azure для вашого додатка
- Розгорнути та очистити власний додаток

---

## Три способи почати проєкт azd

| Початкова точка | Команда | Коли використовувати |
|----------------|---------|-------------|
| **З шаблону** | `azd init --template <name> .` (порожня директорія) | Навчання або початок нового додатку на основі перевіреного зразка |
| **З існуючого коду** | `azd init` (у вашій папці проєкту) | У вас вже є додаток і ви хочете його розгорнути |
| **З Git-репозиторію** | `azd init --from-code` (у клонованому репозиторії) | Використання azd для існуючого репозиторію |

Ви вже практикували перший варіант. Цей урок охоплює другий — найпоширенішу реальну ситуацію.

---

## Крок 1: Запустіть `azd init` у вашому проєкті

Відкрийте термінал **всередині вашої поточної папки проєкту** і виконайте:

```bash
cd my-existing-app
azd init
```

azd запитає, як ви хочете ініціалізувати. Виберіть:

```
? How do you want to initialize your app?
> Use code in the current directory
  Select a template
```

Оберіть **"Use code in the current directory."** azd сканує вашу папку, визначає мову та фреймворк, і пропонує хост.

### Що виявляє azd

azd шукає сигнали додатка, такі як `package.json`, `requirements.txt`, `pom.xml`, `*.csproj`, або `Dockerfile`. Потік з коду не є універсальним майстром вибору хоста для кожної підтримуваної цільової платформи розгортання:

| Ваш додаток | Ймовірний виявлений хост |
|----------|----------------------|
| Підтримуваний Node.js / Python / .NET веб-додаток | Зазвичай Azure Container Apps; перевірте згенероване визначення |
| Контейнеризований додаток (`Dockerfile`) | Azure Container Apps |
| Функціональний додаток або проект Static Web Apps | Використовуйте відповідний шаблон або створюйте `azure.yaml` та інфраструктуру, якщо потік з коду не підтримує вашу структуру |

Підтвердьте виявлені сервіс(и), azd згенерує потрібні файли.

---

## Крок 2: Зрозумійте, що створив azd

Після ініціалізації проінспектуйте `azure.yaml`. Потік згенерованої інфраструктури може приховувати інфраструктуру доти, доки ви не виконаєте `azd infra generate`; не припускайте, що `infra/` вже існує:

```
my-existing-app/
├── azure.yaml          # ← NEW: tells azd what to deploy and where
├── infra/              # Materialized with azd infra generate when using implicit infrastructure
│   ├── main.bicep
│   └── main.parameters.json
├── src/ (your code)    # unchanged
└── ...                 # your existing files, untouched
```

### `azure.yaml` — визначення проєкту

Це серце проєкту azd. Наступне **ілюстративне визначення App Service** вимагає відповідної інфраструктури App Service; це не причина змінювати хост Container Apps без зміни інфраструктури:

```yaml
# azure.yaml
name: my-existing-app
services:
  web:
    project: ./src           # path to your app code
    language: js             # js | python | dotnet | java
    host: appservice         # appservice | containerapp | function | staticwebapp
```

Блок `services` є ключовою частиною: кожен запис зіставляє папку вашого коду з хостом Azure. Якщо у вашого додатка є і фронтенд, і API, у вас буде два сервіси.

### `infra/` — ваші ресурси Azure як код

Папка `infra/` містить файли Bicep, які визначають Azure ресурси, необхідні вашому додатку (App Service, база даних тощо). Вам не потрібно писати їх вручну — azd генерує робочу стартову точку. Ви *можете* редагувати їх пізніше, щоб додати ресурси або посилити безпеку (розглянуто в [Розділі 4](../chapter-04-infrastructure/README.md)).

> **Порада:** Хочете побачити або налаштувати згенеровану інфраструктуру перед розгортанням? Виконайте `azd infra generate` (також доступно як `azd infra synth`), щоб записати IaC на диск для перегляду та контролю версій.

---

## Крок 3: Встановіть необхідну конфігурацію

Якщо вашому додатку потрібні настройки або секрети (рядок з’єднання, API-кей), не захардкоджуйте їх. Використовуйте значення середовища:

```bash
# Create an environment
azd env new dev

# Set a non-secret value
azd env set API_VERSION 1.0.0
```

Це зберігає локальне значення лише. Щоб вплинути на додаток, явно використовуйте його в параметрах інфраструктури, підтримуваних налаштуваннях сервісу або хуках; встановлення довільної змінної не конфігурує розгорнуте середовище виконання.

Для реальних секретів зберігайте їх у Key Vault і посилайтеся на них з інфраструктури — див. [Розділ 3: Конфігурація та автентифікація](../chapter-03-configuration/authsecurity.md).

---

## Крок 4: Розгорніть

Використовуйте тепер той самий робочий процес, який ви вже знаєте:

```bash
# Authenticate (required for azd)
azd auth login

# Preview the resources that will be created
azd provision --preview

# Provision infrastructure and deploy your code
azd up
```

Коли завершиться, azd виведе URL вашого додатку. Перевірте його так само, як будь-який додаток azd:

```bash
azd show           # show endpoints
azd monitor --logs # check logs if needed
```

## Поширені проблеми для першого запуску

| Симптом | Ймовірна причина | Виправлення |
|---------|--------------|-----|
| azd не виявив мій додаток | Відсутній маніфест (наприклад, `package.json`) | Додайте маніфест або виберіть хост вручну під час `azd init` |
| Збірка не вдається під час `azd up` | Додаток потребує кроку збірки | Налаштуйте скрипти пакунку додатку або сервісний хук `prepackage`; використовуйте `dist` для виводу розгортання, а не `buildCommand`/`outputPath` |
| Додаток запускається, але повертає помилки | Відсутня конфігурація/секрет | Підключіть значення в налаштування додатку під час виконання або посилання на Key Vault; одного лише `azd env set` недостатньо |
| Обрано неправильний хост | Автовизначення не відповідає вашим потребам | Змініть і `host:`, і відповідну інфраструктуру, або оберіть відповідний шаблон |

Для більш детального ознайомлення перегляньте [Розділ 7: Усунення неполадок](../chapter-07-troubleshooting/README.md).

---

## Очистка

```bash
azd down --force --purge
```

---

## Підсумок

- `azd init` → **"Use code in the current directory"** додає azd до додатку, який у вас вже є.
- `azure.yaml` зіставляє папки вашого коду з хостами Azure; `infra/` визначає ресурси як Bicep.
- `azd infra generate` дозволяє переглядати або налаштовувати згенеровану інфраструктуру.
- Після ініціалізації ваш існуючий додаток використовує той самий робочий процес `azd up` / `azd down`, що і додаток на основі шаблону.
