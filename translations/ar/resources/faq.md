## البداية

### س: ما هو Azure Developer CLI (azd)؟
**ج**: Azure Developer CLI (azd) هو أداة سطر أوامر تركز على المطورين تُسرع الوقت الذي تستغرقه لنقل تطبيقك من بيئة التطوير المحلية إلى Azure. توفر أفضل الممارسات من خلال القوالب وتساعد في دورة حياة النشر كاملة.

### س: كيف يختلف azd عن Azure CLI؟
**ج**: 
- **Azure CLI**: أداة عامة لإدارة موارد Azure
- **azd**: أداة تركز على المطورين لسير عمل نشر التطبيقات
- لـ azd سير عمل مصادقة ونشر خاص به؛ Azure CLI هي أداة منفصلة ومكملة
- يشمل azd قوالب وإدارة البيئات وأتمتة النشر

### س: هل أحتاج إلى تثبيت Azure CLI لاستخدام azd؟
**ج**: ليس لسير عمل AZD الأساسي. قم بالمصادقة باستخدام `azd auth login`. قم بتثبيت Azure CLI بشكل منفصل عندما يقوم قالب محدد أو تمرين بتشغيل أوامر `az` صراحةً.

### س: ما لغات البرمجة التي يدعمها azd؟
**ج**: azd مستقل عن اللغة. يعمل مع:
- Node.js/JavaScript/TypeScript
- Python
- .NET/C#
- Java
- Go
- PHP
- المواقع الثابتة
- التطبيقات المحوَّطة بالحاويات

### س: هل يمكنني استخدام azd مع مشاريع موجودة؟
**ج**: نعم! يمكنك إما:
1. استخدام `azd init` لإضافة تكوين azd إلى مشاريع موجودة
2. تكييف المشاريع الحالية لتتناسب مع بنية قوالب azd
3. إنشاء قوالب مخصصة بناءً على الهندسة الحالية لديك

### س: ماذا تغير مع توفر ملحق Foundry بشكل عام؟
**ج**: وصل `microsoft.foundry` للحزمة إلى الإصدار 1.0 والتوفر العام في 5 نوفمبر 2026. باستخدام AZD 1.37.0+، استخدم `azd ext install microsoft.foundry` لتثبيت سبعة ملحقات أساسية للوكلاء، الاتصالات، المفتش، المشاريع، الروتينات، المهارات، وصناديق الأدوات. ليست مساحة أسماء أوامر جديدة، ومكوناتها تتوفر بإصدارات مستقلة. التقييمات، مجموعات البيانات، التخصيص الدقيق، والنماذج المخصصة تُثبت بشكل منفصل؛ الميزات التجريبية الاختيارية لا تصبح متاحة تجاريًا فقط لأن الحزمة متاحة تجاريًا.

يستخدم [شرح الوكيل المستضاف](../docs/chapter-02-ai-development/microsoft-foundry-integration.md#hosted-agent-walkthrough-ga) Python 3.13+ و uv الحالي. `azd ai agent run` يفتح Agent Inspector محليًا، لكن استدعاءات النماذج لا تزال تستخدم Azure وتتكبد رسومًا. وضع التعليمات البرمجية `azd deploy` يرفع المصدر للبناء عن بعد دون الحاجة إلى بناء حاوية محليًا.

### س: هل يقوم `azd down` بإزالة وكيل مستضاف من مشروع Foundry قائم؟
**ج**: ليس لمسار مشروع إعادة الاستخدام الموضح في التشغيل السريع للوكيل المستضاف: يترك المشروع والوكيل المستضاف والموارد الأخرى كما هي. قم بإزالة الموارد غير المرغوب فيها بشكل منفصل دون حذف الموارد المشتركة. إذا أنشأ البيئة مشروع Foundry جديدًا، `azd down` يحذف مجموعة الموارد وكل ما بداخلها. راجع [إرشادات التنظيف](../docs/chapter-02-ai-development/microsoft-foundry-integration.md#7-clean-up-deliberately) ومطالبات الحذف قبل التأكيد.

## المصادقة والوصول

### س: كيف أقوم بالمصادقة مع Azure باستخدام azd؟
**ج**: استخدم `azd auth login` الذي سيفتح نافذة المتصفح لمصادقة Azure. بالنسبة لسيناريوهات CI/CD، استخدم مبادئ الخدمة أو الهويات المُدارة.

### س: هل يمكنني استخدام azd مع اشتراكات Azure متعددة؟
**ج**: نعم. استخدم `azd env set AZURE_SUBSCRIPTION_ID <subscription-id>` لتحديد الاشتراك الذي تريد استخدامه لكل بيئة.

### س: ما الأذونات التي أحتاجها للنشر باستخدام azd؟
**ج**: عادة تحتاج إلى:
- دور **مساهم** على مجموعة الموارد أو الاشتراك
- دور **مسؤول وصول المستخدم** إذا كنت تنشر موارد تتطلب تعيينات أدوار
- تختلف الأذونات المحددة حسب القالب والموارد التي يتم نشرها

### س: هل يمكنني استخدام azd في خطوط أنابيب CI/CD؟
**ج**: بالتأكيد! تم تصميم azd للتكامل في CI/CD. استخدم مبادئ الخدمة للمصادقة واضبط متغيرات البيئة للتكوين.

### س: كيف أتعامل مع المصادقة في إجراءات GitHub؟
**ج**: الأفضل استخدام اتحاد هوية عبء العمل (OIDC)، مُعد باستخدام `azd pipeline config`. يثبت سير العمل الذي تم إنشاؤه AZD ويصادق AZD مباشرةً بهوية موحدة. خطوة `azure/login` وحدها لا تنشئ تسجيل دخول لـ AZD. خطوة تسجيل الدخول ضمن وظيفة موجودة هي:
```yaml
permissions:
  contents: read
  id-token: write
steps:
  - uses: actions/checkout@v7
  - uses: Azure/setup-azd@v2
  - run: >-
      azd auth login
      --client-id "${{ vars.AZURE_CLIENT_ID }}"
      --tenant-id "${{ vars.AZURE_TENANT_ID }}"
      --federated-credential-provider github
```

قم بالتوفير أو النشر بعد تسجيل الدخول، مع تكوين البيئة والاشتراك والموقع المقصود في AZD. يجب أن تثق بيانات اعتماد الهوية الموحدة في مستودع/مرجع سير العمل أو بيئة GitHub، ويجب أن تسمح أدوار Azure الخاصة بها بالعمليات المطلوبة.

## القوالب والمشاريع

### س: أين أجد قوالب azd؟
**ج**: 
- القوالب الرسمية ومجتمعية: [Awesome AZD](https://azure.github.io/awesome-azd/)
- قوالب المجتمع: ابحث في GitHub عن "azd-template"
- استخدم `azd template list` لتصفح القوالب المتاحة

### س: كيف أنشئ قالبًا مخصصًا؟
**ج**: 
1. ابدأ بهيكل قالب موجود
2. عدل `azure.yaml`، ملفات البنية التحتية، وكود التطبيق
3. اختبر جيدًا باستخدام `azd up`
4. انشر إلى GitHub باستخدام الوسوم المناسبة

### س: هل يمكنني استخدام azd بدون قالب؟
**ج**: نعم، استخدم `azd init` في مشروع موجود لإنشاء ملفات التكوين اللازمة. ستحتاج إلى تكوين `azure.yaml` وملفات البنية التحتية يدويًا.

### س: ما الفرق بين القوالب الرسمية والمجتمعية؟
**ج**: 
- **القوالب الرسمية**: مدعومة من مايكروسوفت، محدثة بانتظام، توثيق شامل
- **القوالب المجتمعية**: أنشأها المطورون، قد تحتوي على حالات استخدام متخصصة، جودة وصيانة متفاوتة

### س: كيف أحدّث قالبًا في مشروعي؟
**ج**: القوالب لا تُحدَّث تلقائيًا. يمكنك:
1. مقارنة ودمج التغييرات يدويًا من القالب الأصلي
2. البدء من جديد باستخدام `azd init` مع القالب المحدث
3. اختيار تحسينات محددة من القوالب المحدثة

## النشر والبنية التحتية

### س: ما خدمات Azure التي يمكن لـ azd نشرها؟
**ج**: يمكن لـ azd نشر أي خدمة Azure من خلال قوالب Bicep/ARM، بما في ذلك:
- خدمات التطبيقات، التطبيقات الحاوية، الوظائف
- قواعد البيانات (SQL، PostgreSQL، Cosmos DB)
- التخزين، مخزن المفاتيح، Application Insights
- موارد الشبكات، الأمان، والمراقبة

### س: هل يمكنني النشر إلى مناطق متعددة؟
**ج**: نعم، قم بتكوين مناطق متعددة في قوالب Bicep الخاصة بك واضبط معلمة الموقع بشكل مناسب لكل بيئة.

### س: كيف أتعامل مع ترحيل مخططات قاعدة البيانات؟
**ج**: استخدم خطافات النشر في `azure.yaml`:
```yaml
hooks:
  postdeploy:
    posix:
      run: ./scripts/migrate-database.sh
    windows:
      run: ./scripts/migrate-database.ps1
```

### س: هل يمكنني نشر البنية التحتية فقط بدون التطبيقات؟
**ج**: نعم، استخدم `azd provision` لنشر مكونات البنية التحتية فقط المعرفة في قوالبك.

### س: كيف أنشر إلى موارد Azure موجودة؟
**ج**: نعم، عندما يدعم القالب ذلك. أشر إلى الموارد الموجودة باستخدام تصريحات `existing` في Bicep أو معلمات الموارد الموجودة الموثقة في القالب، وقم بتوجيه خدمات التطبيق إلى أهدافها المقصودة. هذا لا يستورد ملكية أو ينشئ أذونات مفقودة تلقائيًا. راجع القالب قبل النشر.

### س: هل يمكنني استخدام Terraform بدلًا من Bicep؟
**ج**: نعم. يدعم AZD Terraform بالإضافة إلى Bicep. اختر قالبًا مبنيًا على Terraform أو قم بتكوين `infra.provider: terraform` في `azure.yaml`، مع ملفات Terraform المناسبة وتكوين الحالة/الخلفية. انظر [سير عمل Terraform](https://learn.microsoft.com/azure/developer/azure-developer-cli/use-terraform-for-azd).

## التكوين والبيئات

### س: كيف أدير بيئات مختلفة (تطوير، اختبار، إنتاج)؟
**ج**: أنشئ بيئات منفصلة باستخدام `azd env new <environment-name>` وخصص إعدادات مختلفة لكل منها:
```bash
azd env new development
azd env new staging  
azd env new production
```

### س: أين يتم تخزين تكوينات البيئة؟
**ج**: في مجلد `.azure` ضمن دليل مشروعك. لكل بيئة مجلد خاص يحتوي على ملفات التكوين.

### س: كيف أعيّن تكوينًا خاصًا بكل بيئة؟
**ج**: استخدم `azd env set` لتكوين متغيرات البيئة:
```bash
azd env set AZURE_LOCATION eastus
azd env set DATABASE_TIER Basic
```

### س: هل يمكنني مشاركة تكوينات البيئة بين أعضاء الفريق؟
**ج**: يحتوي مجلد `.azure` على معلومات حساسة ولا يجب الالتزام به في نظام التحكم بالنسخ. بدلاً من ذلك:
1. وثق متغيرات البيئة المطلوبة
2. استخدم نصوص النشر لضبط البيئات
3. استخدم Azure Key Vault للتكوين الحساس

### س: كيف أتجاوز الإعدادات الافتراضية للقالب؟
**ج**: قم بتعيين متغيرات البيئة التي تتوافق مع معلمات القالب:
```bash
azd env set AZURE_LOCATION westus2
azd env set SKU_NAME "B1"
```

فقط المتغيرات المستخدمة من القالب تؤثر على النشر. `SKU_NAME` أعلاه هو مثال على إدخال مخصص، وليس إعدادًا عالميًا لـ AZD.

## استكشاف الأخطاء وإصلاحها

### س: لماذا يفشل `azd up`؟
**ج**: الأسباب الشائعة:
1. **مشاكل المصادقة**: شغّل `azd auth login`
2. **أذونات غير كافية**: راجع تعيينات الأدوار في Azure
3. **تعارضات تسمية الموارد**: راجع المورد المتعارض ومدخلات تسمية القالب؛ أنشئ بيئة منفصلة باستخدام `azd env new` عند الحاجة للعزل
4. **مشكلة الحصة/السعة**: تحقق من التوافر الإقليمي
5. **أخطاء في القالب**: تحقق من صحة قوالب Bicep

### س: كيف أقوم بتصحيح فشل عمليات النشر؟
**ج**: 
1. استخدم `azd deploy --debug` للمخرجات التفصيلية
2. راجع سجل النشر في بوابة Azure
3. راجع سجل النشاط في بوابة Azure
4. استخدم `azd show` لعرض حالة البيئة الحالية

### س: لماذا لا تعمل متغيرات البيئة الخاصة بي؟
**ج**: تحقق من:
1. تطابق أسماء المتغيرات مع معلمات القالب بدقة
2. أن القيم مقتبسة بشكل صحيح إذا احتوت على فراغات
3. تم اختيار البيئة: `azd env select <environment>`
4. تم تعيين المتغيرات في البيئة الصحيحة

### س: كيف أنظف عمليات نشر فشلت؟
**ج**: 
```bash
azd down
```
 راجع البيئة المختارة وتأكيد الحذف أولاً. هذا يحذف موارد Azure المُوفرة، وليس تكوين بيئة `.azure` المحلي. يطلب `--purge` أيضًا الحذف الدائم للموارد المحذوفة دعمًا ويمكن حظره بواسطة الحماية من الحفظ/المحو؛ ليس هذا خطوة استرداد روتينية.

### س: لماذا لا يمكن الوصول إلى تطبيقي بعد النشر؟
**ج**: تحقق من:
1. اكتمال النشر بنجاح
2. تشغيل التطبيق (راجع السجلات في بوابة Azure)
3. سماح مجموعات أمان الشبكة للحركة
4. تكوين DNS/النطاقات المخصصة بشكل صحيح

## التكلفة والفواتير

### س: كم ستكلف نشرات azd؟
**ج**: تعتمد التكاليف على:
- خدمات Azure التي يتم نشرها
- مستويات/أنواع الخدمة المختارة
- اختلافات التسعير الإقليمية
- أنماط الاستخدام

استخدم [حاسبة أسعار Azure](https://azure.microsoft.com/pricing/calculator/) للتقديرات.

### س: كيف أتحكم في التكاليف في نشرات azd؟
**ج**: 
1. استخدم مستويات SKUs منخفضة للبيئات التطويرية
2. اضبط ميزانيات وتنبيهات Azure
3. استخدم `azd down` لإزالة الموارد عند عدم الحاجة
4. اختر المناطق المناسبة (تختلف التكاليف حسب الموقع)
5. استخدم أدوات إدارة تكلفة Azure

### س: هل توجد خيارات مجانية لقوالب azd؟
**ج**: تحتوي بعض الخدمات على خطط مجانية أو منح شهرية، مع مراعاة الأهلية وخطة الاستضافة والمنطقة والاشتراك. هذه لا تجعل القالب بأكمله مجانياً: قد تفرض قواعد البيانات، البحث، الشبكات، التسجيل، القياس، واستنتاج النماذج رسومًا بشكل منفصل. تحقق من [قائمة خدمات Azure المجانية](https://azure.microsoft.com/free/) والأسعار الحالية لكل مورد قبل النشر.

### س: كيف يمكنني تقدير التكاليف قبل النشر؟
**ج**: 
1. راجع `main.bicep` للقالب لرؤية الموارد التي يتم إنشاؤها
2. استخدم حاسبة أسعار Azure مع خطط SKU محددة
3. انشر أولاً في بيئة تطوير لمراقبة التكاليف الفعلية
4. استخدم إدارة تكاليف Azure لتحليل التكاليف التفصيلي

## أفضل الممارسات

### س: ما هي أفضل الممارسات لهكيل مشروع azd؟
**ج**: 
1. احتفظ برمز التطبيق منفصلاً عن البنية التحتية
2. استخدم أسماء خدمات ذات معنى في `azure.yaml`
3. نفذ معالجة الأخطاء المناسبة في سكريبتات البناء
4. استخدام تكوين مخصص للبيئات
5. تضمين توثيق شامل

### س: كيف يجب أن أنظم خدمات متعددة في azd؟
**ج**: استخدم الهيكلية الموصى بها:
```
├── src/
│   ├── web/          # Frontend service
│   ├── api/          # Backend service  
│   └── worker/       # Background service
├── infra/            # Infrastructure templates
├── azure.yaml        # azd configuration
└── README.md         # Project documentation
```

### س: هل يجب عليّ الالتزام بمجلد `.azure` في نظام التحكم بالإصدارات؟
**ج**: **لا!** يحتوي المجلد `.azure` على معلومات حساسة. أضفه إلى `.gitignore`:
```gitignore
.azure/
```

### س: كيف أتعامل مع الأسرار والتكوين الحساس؟
**ج**: 
1. استخدم Azure Key Vault Secrets
2. أشر إلى أسرار Key Vault في تكوين التطبيق
3. لا تلتزم بالأسرار في نظام التحكم بالإصدارات أبدًا
4. استخدم الهويات المُدارة للمصادقة بين الخدمات

### س: ما هو الأسلوب الموصى به لـ CI/CD مع azd؟
**ج**: 
1. استخدم بيئات منفصلة لكل مرحلة (تطوير/اختبار/إنتاج)
2. نفذ اختبارات تلقائية قبل النشر
3. استخدم أذونات الخدمة للمصادقة
4. خزن التكوينات الحساسة في أسرار/متغيرات خطوط الأنابيب
5. نفذ بوابات الموافقة لنشر الإنتاج

## مواضيع متقدمة

### س: هل يمكنني توسيع azd بوظائف مخصصة؟
**ج**: نعم، من خلال وصلات النشر في `azure.yaml`:
```yaml
hooks:
  predeploy:
    run: ./scripts/custom-setup.sh
  postdeploy:
    run: ./scripts/custom-config.sh
```

### س: كيف أدمج azd في عمليات DevOps الحالية؟
**ج**: 
1. استخدم أوامر azd في سكريبتات خطوط الأنابيب الحالية
2. اعتمد قوالب azd كنمط موحد عبر الفرق
3. دمج المراقبة والتنبيهات الحالية
4. استخدم ناتج JSON من azd للتكامل مع خطوط الأنابيب

### س: هل يمكنني استخدام azd مع Azure DevOps؟
**ج**: نعم، azd يعمل مع أي نظام CI/CD. أنشئ خطوط أنابيب Azure DevOps تستخدم أوامر azd.

### س: كيف أساهم في azd أو أنشئ قوالب مجتمعية؟
**ج**: 
1. **أداة azd**: ساهم في [Azure/azure-dev](https://github.com/Azure/azure-dev)
2. **القوالب**: اتبع [تعليمات مساهمة في معرض Awesome AZD](https://github.com/Azure/awesome-azd#3-contribute-to-gallery)
3. **التوثيق**: ساهم في الوثائق على [MicrosoftDocs/azure-dev-docs](https://github.com/MicrosoftDocs/azure-dev-docs)

### س: ما هي خارطة طريق azd؟
**ج**: تحقق من [خارطة الطريق الرسمية](https://github.com/Azure/azure-dev/projects) للمزايا والتحسينات المخططة.

### س: كيف أهاجر من أدوات نشر أخرى إلى azd؟
**ج**: 
1. تحليل بنية النشر الحالية
2. إنشاء قوالب Bicep مكافئة
3. إعداد `azure.yaml` لمطابقة الخدمات الحالية
4. اختبار شامل في بيئة التطوير
5. الهجرة التدريجية للبيئات
