# أحضر تطبيقك الخاص - إضافة azd إلى مشروع موجود

**التنقل في الفصل:**
- **📚 الصفحة الرئيسية للدورة**: [AZD للمبتدئين](../../README.md)
- **📖 الفصل الحالي**: الفصل 1 - الأساسيات والبدء السريع
- **⬅️ السابق**: [مشروعك الأول](first-project.md)
- **➡️ التالي**: [حاويات المطور ومساحات الكود](dev-containers.md)

> مراجعة الأمر والتكوين الهدف: `azd 1.37.2` (نوفمبر 2026). تعتمد الملفات المُنشأة على التطبيق المكتشف؛ لم يتم تنفيذ نشر Azure في هذه المراجعة.

## مقدمة

في [مشروعك الأول](first-project.md) قمت بنشر تطبيق بدءًا من قالب. لكن في معظم الأحيان لديك بالفعل *تطبيق* — API لـ Node.js، خدمة Python Flask، تطبيق ويب .NET — موجود في مجلد على جهازك. توضح هذه الدرس كيفية إضافة azd إلى هذا الكود الموجود حتى تتمكن من نشره باستخدام `azd up`، دون الحاجة إلى قالب.

## أهداف التعلم

بنهاية هذا الدرس، ستتمكن من:
- فهم الطرق الثلاث لبدء مشروع azd
- تشغيل `azd init` داخل قاعدة كود موجودة
- فهم ما تقوم به `azure.yaml` ومجلد `infra/` لتطبيقك
- معرفة متى تسمح لـ azd بإنشاء البنية التحتية مقابل كتابة بنية تحتية خاصة بك
- نشر تطبيقك الموجود إلى Azure باستخدام `azd up`

## نتائج التعلم

بعد إكمال هذا الدرس، ستتمكن من:
- تهيئة azd في مشروع لديك بالفعل
- قراءة وتحرير ملف `azure.yaml` أساسي
- إنشاء بنية تحتية أولية باستخدام `azd infra generate`
- اختيار مضيف Azure مناسب لتطبيقك
- نشر وتنظيف تطبيقك الخاص

## ثلاث طرق لبدء مشروع azd

| نقطة البداية | الأمر | متى تستخدم |
|----------------|---------|-------------|
| **من قالب** | `azd init --template <name> .` (مجلد فارغ) | التعلم، أو بدء تطبيق جديد من نموذج مثبت |
| **من الكود الموجود لديك** | `azd init` (في مجلد مشروعك) | لديك تطبيق بالفعل وترغب في نشره |
| **من مستودع Git** | `azd init --from-code` (في مستودع مستنسخ) | تبني azd لمستودع موجود |

لقد تدربت بالفعل على الخيار الأول. يغطي هذا الدرس الخيار الثاني — وهو السيناريو الأكثر شيوعًا في العالم الحقيقي.

## الخطوة 1: تشغيل `azd init` في مشروعك

افتح نافذة طرفية **داخل مجلد مشروعك الموجود** وشغل:

```bash
cd my-existing-app
azd init
```

سيسألك azd عن كيفية التهيئة. اختر:

```
? How do you want to initialize your app?
> Use code in the current directory
  Select a template
```

اختر **"استخدام الكود في الدليل الحالي."** ثم يقوم azd بمسح مجلدك، واكتشاف لغتك وإطار العمل الخاص بك، ويقترح مضيفًا.

### ما يكتشفه azd

يبحث azd عن إشارات التطبيق مثل `package.json`، `requirements.txt`، `pom.xml`، `*.csproj`، أو ملف `Dockerfile`. تدفق من الكود ليس معالج اختيار المضيف العام لكل هدف نشر مدعوم:

| تطبيقك | المضيف المحتمل الاكتشاف |
|----------|----------------------|
| تطبيق ويب Node.js / Python / .NET مدعوم | عادةً Azure Container Apps؛ تفقد التعريف الذي تم إنشاؤه |
| تطبيق حاوية (`Dockerfile`) | Azure Container Apps |
| تطبيق دالة أو مشروع ويب ثابت | استخدم قالب مطابق أو أنشئ `azure.yaml` وبنية تحتية إذا لم يدعم تدفق من الكود تخطيطك |

أكد الخدمة/الخدمات المكتشفة، ويقوم azd بتجهيز الملفات التي تحتاجها.

---

## الخطوة 2: فهم ما أنشأه azd

بعد التهيئة، افحص `azure.yaml`. تدفق البنية التحتية المُنشأة يمكن أن يبقي البنية التحتية ضمنية حتى تقوم بتشغيل `azd infra generate`؛ لا تفترض أن `infra/` موجودة مسبقًا:

```
my-existing-app/
├── azure.yaml          # ← NEW: tells azd what to deploy and where
├── infra/              # Materialized with azd infra generate when using implicit infrastructure
│   ├── main.bicep
│   └── main.parameters.json
├── src/ (your code)    # unchanged
└── ...                 # your existing files, untouched
```

### `azure.yaml` — تعريف المشروع

هذه هي قلب مشروع azd. التعريف التالي **الخدمة التطبيقية الإيضاحية** يتطلب بنية تحتية مطابقة لخدمة التطبيقات؛ ليس سببًا لتغيير مضيف Azure Container Apps المنشأ دون تغيير البنية التحتية:

```yaml
# azure.yaml
name: my-existing-app
services:
  web:
    project: ./src           # path to your app code
    language: js             # js | python | dotnet | java
    host: appservice         # appservice | containerapp | function | staticwebapp
```

قسم `services` هو الجزء الرئيسي: كل مدخل يربط مجلد الكود الخاص بك بمضيف Azure. إذا كان لدى تطبيقك واجهة أمامية و API، فسيكون لديك خدمتان.

### `infra/` — موارد Azure ككود

يحتوي مجلد `infra/` على ملفات Bicep التي تحدد موارد Azure التي يحتاجها تطبيقك (خدمة التطبيق، قاعدة البيانات، إلخ). لست مضطرًا لكتابة هذه الملفات يدويًا—يقوم azd بإنشاء نقطة بداية قابلة للعمل. يمكنك *تحريرها* لاحقًا لإضافة موارد أو تشديد الأمان (مغطى في [الفصل 4](../chapter-04-infrastructure/README.md)).

> **نصيحة:** هل تريد رؤية أو تخصيص البنية التحتية المولدة قبل النشر؟ شغل `azd infra generate` (متوفر أيضًا كـ `azd infra synth`) لكتابة IaC على القرص لتتمكن من مراجعتها ومراقبتها بإصدار.

## الخطوة 3: تعيين التكوين المطلوب

إذا كان تطبيقك يحتاج إلى إعدادات أو أسرار (سلسلة اتصال، مفتاح API)، فلا تقم بترميزها مباشرة. استخدم قيم البيئة:

```bash
# Create an environment
azd env new dev

# Set a non-secret value
azd env set API_VERSION 1.0.0
```

يخزن هذا قيمة محلية فقط. لتؤثر على التطبيق، يجب استهلاكها صراحةً في معلمات البنية التحتية، أو إعداد خدمة مدعومة، أو هوك؛ تعيين متغير عشوائي لا يهيئ وقت تشغيل النشر.

للأسرار الحقيقية، قم بتخزينها في Key Vault وارجع إليها من بنيتك التحتية—انظر [الفصل 3: التكوين والمصادقة](../chapter-03-configuration/authsecurity.md).

## الخطوة 4: النشر

الآن استخدم نفس سير العمل الذي تعرفه بالفعل:

```bash
# Authenticate (required for azd)
azd auth login

# Preview the resources that will be created
azd provision --preview

# Provision infrastructure and deploy your code
azd up
```

عندما ينتهي، يطبع azd عنوان URL الخاص بتطبيقك. تحقق منه بنفس طريقة أي تطبيق azd:

```bash
azd show           # show endpoints
azd monitor --logs # check logs if needed
```

## مشكلات شائعة في المحاولة الأولى

| العَرَض | السبب المحتمل | الإصلاح |
|---------|--------------|-----|
| azd لم يكتشف تطبيقي | الملف التعريفي مفقود (مثل `package.json`) | أضف الملف التعريفي، أو اختر المضيف يدويًا أثناء `azd init` |
| فشل البناء أثناء `azd up` | التطبيق يحتاج خطوة بناء | قم بتكوين نصوص الحزمة الخاصة بالتطبيق أو هوك خدمة `prepackage`؛ استخدم `dist` لمخرجات النشر، لا `buildCommand`/`outputPath` |
| يبدأ التطبيق لكنه يرجع أخطاء | تكوين/سر مفقود | اربط القيم في إعدادات التطبيق أثناء التشغيل أو مرجع Key Vault؛ `azd env set` لوحده غير كافٍ |
| تم اختيار المضيف الخطأ | الكشف التلقائي لا يتطابق مع احتياجاتك | غيّر كل من `host:` والبنية التحتية المقابلة، أو اختر قالبًا مطابقًا |

للمزيد، انظر [الفصل 7: استكشاف الأخطاء وإصلاحها](../chapter-07-troubleshooting/README.md).

## التنظيف

```bash
azd down --force --purge
```

---

## الملخص

- `azd init` → **"استخدام الكود في الدليل الحالي"** يضيف azd إلى تطبيق لديك بالفعل.
- `azure.yaml` يربط مجلدات الكود الخاصة بك بمضيفي Azure؛ `infra/` يحدد الموارد كـ Bicep.
- `azd infra generate` يتيح لك مراجعة أو تخصيص البنية التحتية المولدة.
- بمجرد التهيئة، يستخدم تطبيقك الحالي نفس سير العمل `azd up` / `azd down` كالتطبيق المستند إلى القالب تمامًا.
