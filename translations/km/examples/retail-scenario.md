## ទិដ្ឋភាពទូទៅ

**គោលបំណង៖** រៀបចំប្រព័ន្ធគាំទ្រអតិថិជនមានភ្នាក់ងារអតិថិជន និងភ្នាក់ងារចំណូល ដើម្បីកំណត់ថា
ទ្រព្យសម្បត្តិប្លុកផ្តល់អ្វីខ្លះ និងគ្រោងសន្សំពាណិជ្ជកម្ម(contracts) ការត្រួតពិនិត្យដែលអវត្តមាន។


**អ្នកទស្សនា:** អ្នកអwickរ៉ា ដែលបានបញ្ចប់ការងារផ្ទាល់ខ្លួន
[chat sample](../../../examples/azure-openai-chat) និង [two-service container sample](../../../examples/container-app/microservices)។
អនុញ្ញាតឱ្យចំណាយពេល ២-៣ ម៉ោងសម្រាប់ការសិក្សារចនាសម្ព័ន្ធ។ ការសាងសង់កម្មវិធីគឺជាព្រឹត្តិការណ៍ផ្សេងទៀត៖ ៨០-១២០ ម៉ោងអភិវឌ្ឍន៍គឺជាការប៉ាន់ប្រមាណផែនការជាចំណុចយោងសម្រាប់អ្នកអភិវឌ្ឍមានបទពិសោធន៍, **មិនមែនជារស្មីបញ្ចេញ**; ការកែលម្អការផលិត, សាកល្បង, ការត្រួតពិនិត្យសុវត្ថិភាព, និងការប្រតិបត្តិការត្រូវការភារកិច្ចបន្ថែម។




### លទ្ធផលការសិក្សា

- អធិប្បាយអំពីការបញ្ជូន, ការប្រឹងប្រែង, សិទ្ធិឧបករណ៍, និងកម្មសិទ្ធិការពិភាក្សា។
- ធ្វើការបំបែករៀងមួយនៃម៉ូដែលណាម, ឈ្មោះប្រព័ន្ធ, ជំនាន់ API, និងជំនាន់ ARM។
- រចនាកម្រងលិខិតពង្រីក និងចូលប្រមូលពួកវាក្នុងវិមាត្រចំណុចវ៉ិចទ័រដូចគ្នា។
- កំណត់តម្រូវការ​ដែលអាចបញ្ជាក់បានសង្ខេបមុខងារ, ការប៉ាន់ប្រមាណ, និងការស្ដារឡើងវិញក្រោយបរាជ័យ។
- បំបែកគោលបំណងរចនាសម្ព័ន្ធជាជម្រើសពីធនធានដែលបានផ្គត់ផ្គង់ជាក់ស្តែង។

## រចនាសម្ព័ន្ធដំណោះស្រាយ

```mermaid
flowchart TB
    User[Customer] --> Frontend[Frontend — must build]
    Frontend --> Router[Authenticated router — must build]
    Router --> Customer[Customer agent — must build]
    Router --> Inventory[Inventory agent — must build]
    Customer --> Chat[Primary chat deployment]
    Inventory --> Mini[Optional mini deployment]
    Customer --> Search[AI Search — empty service]
    Inventory --> Stock[Inventory source + tool — must build]
    Search --> Index[Index + ingestion — must build]
    Blob[Blob documents] --> Processor[Document pipeline — must build]
    Processor --> DocAI[Document Intelligence]
    Processor --> Embeddings[Optional embeddings deployment]
    Processor --> Index
    Router --> Cosmos[Cosmos DB chat-history container]
    Router -. instrument .-> Insights[Optional Application Insights]
    Customer -. instrument .-> Insights
    Eval[Evaluation runner — must build] --> Grader[Grader deployment]
```

នេះជារចនាសម្ព័ន្ធកម្មវិធីគោលដៅមួយ, មិនមែនជារូបភាពជាសេវាកម្មភ្នាក់ងាររត់។
ស្នូល ARM បង្កើតសេវាកម្មរង និងធុងបន្ទុកស្នូលពីរ​តែមួយ។ Front Door, ការចុះបញ្ជី, អត្តសញ្ញាណគ្រប់គ្រង, ការចាត់តួនាទី,
ចំណុចបញ្ចប់ឯកជន, ការបរាជ័យប្តូរ, ការត្រួតពិនិត្យកម្មវិធី, និងការព្រមានមិនត្រូវបានបញ្ចូល។

ទាំងឡាយនៅក្នុងស្ទោងនេះទេ។  

## លំហាត់រចនាបទជាក់ស្តែង  

នេះគឺជាលំហាត់​​ **ស្ថាបត្យកម្ម** មិនមែនជាការទាមទារលេខកូដ starters លក់រាយអាចបញ្ចេញបាននោះទេ។  

### លំហាត់ទី 1៖ ត្រួតពិនិត្យស្មើនឹងព្រំដែន  

**ចំណុចចាប់ផ្តើម៖**​ ផ្ទាំងឯកសារ 3 នៅក្នុង `retail-multiagent-arm-template/`។  
**គោលបំណង៖** ផ្សះផ្សារពីការផ្ដល់សេវាកម្មពីមុខងារកម្មវិធី។  
បើក `azuredeploy.json` ស្វែងរករូបភាពកុងតেইន័រ និងតម្លៃ `targetPort` ទាំងពីរ,  
បន្ទាប់មករាយបញ្ជីគ្រឿងផ្សំកម្មវិធីដែលខ្វះនៅក្នុងឃ្លាំងគ្មាន។  

**ក្រមបទជោគជ័យ / ចម្លើយ៖** រូបភាពទាំងពីរគឺជា hello-world ជំនួសដែលស្តាប់  
នៅលើព្រិល 80; តំណាង, ផ្ទាំងសន្ទនា UI, អ្នកចាត់ការចរាចរ, សិុវហិច/ការចូលយក, អ្នកវាយតម្លៃ និងអ្នកស្កេន គ្មាន។
សំណើររុករកប្រាក់កំណត់ដើមដោយជោគជ័យមិនបញ្ជាក់តម្លៃ `/chat` ទេ។
**បញ្ហាទូទៅ៖** ពន្យល់ឈ្មោះធនធានដូចជា `retail-router` ជាកូដដែលដំណើរការ។

### ហាត់លំហាត់ 2៖ តាមដានរចនាសម្ព័ន្ធវ៉ិចទ័រ

**ចំណុចចាប់ផ្តើម៖** JSON សុិតខាងលើ។
**គោលដៅ៖** យល់ដឹងពីទំនាក់ទំនងដែន → បprofile → អាល់ហ្គារីធម៍។
ស្វែងរកថាតើតម្លៃណាខ្លះត្រូវផ្លាស់ប្ដូរនៅពេលប្តូរទៅម៉ូដែលអំប៉ុងដែលមាន
ទំហំចេញខុសគ្នា, បន្ទាប់មកពិនិត្យមើលមុខងារ `retrieve`។

**កម្រិតជោគជ័យ / ចម្លើយ៖** ប្ដូរដែន `dimensions` ទៅប្រវែងវ៉ិចទ័រពិតប្រាកដ;
រក្សាតម្លៃ `vectorSearchProfile` ស្របតាមបprofile ដែលបានប្រកាស និង អាល់ហ្គារីធម៍របស់វា;
សំណើ `fields` ត្រូវតែមានឈ្មោះដែនវ៉ិចទ័រ។ បង្កើតមូលដ្ឋានឯកសារវ៉ិចទ័រដែលមានស្រាប់ឡើងវិញ
នៅពេលម៉ូដែលអំប៉ុងផ្លាស់ប្ដូរ។
**បញ្ហាទូទៅ៖** ប្ដូរឈ្មោះម៉ូដែលតែប៉ុណ្ណោះ ប៉ុន្តែនៅតែមិនសមរម្យនឹងវ៉ិចទ័រ។

### ហាត់លំហាត់ 3៖ កំណត់ការប្រលងបរាជ័យ

**ចំណុចចាប់ផ្តើម៖** តារាងភារកិច្ច។
**គោលដៅ៖** ការបញ្ជៀសការជោគជ័យមិនពិតប្រាកដ។
សរសេរព័ត៌មានដែលរំពឹងទុកសម្រាប់ API សារពើភ័ណ្ឌមិនអាចប្រើបាន, សុិតស្វែងរកដែលគ្មានឯកសារចូលរួម,
និងសំណើវាយតម្លៃដែលត្រឡប់មកនូវ HTTP 503។

**កម្រិតជោគជ័យ / ចម្លើយ៖** មិនបង្កើតតម្លៃសារពើភ័ណ្ឌ; លែងតបាសច្បាស់ ឬ
ការលើកស្ទួយពេលបរិបទខ្វះ; របាយការណ៍វាយតម្លៃថា មិនអាចដឹកជញ្ជូនដោយសារបំពានឈ្មួញ
ជាងការឆ្លើយតបទៅគុណភាព ឬសុវត្ថិភាព។ បន្ថែមតេស្តដែលអាចដំណើរការបានពេលអ្នកកសាងកម្មវិធី។
**បញ្ហាទូទៅ៖** ចាប់យកករណី excepción ទាំងអស់ និងបន្តដោយចម្លើយទំនេរ។

## ថ្លៃដើម, ការឈឺចាប់ និងការសម្អាត

  ចរាចរអាចសន្សំប្រាក់ទៅតែមែន ប្រសិនបើមានការវាស់ម៉ោងការងារនិងលទ្ធផលគុណភាពយុត្តិធម៌;
  មិនមានការធានាជាក់លាក់សន្សំបានពី 60–80%។ 
- ពិនិត្យមើលភាពរឹតត្បិតម៉ូដែល និងកូតង់មុនពេលផ្តល់; បំបែកកំហុសនៃការអនុញ្ញាត,
  ឈ្មោះdeployment, តំបន់, កំណែម៉ូដែល និងកំណែAPI។
- កុំបើកចំហ់ `setup-data.sh` ខកខាន, បញ្ជា CLI evaluator ឬបញ្ជា `pytest tests/`។
  ការអនុវត្តន៍ទាំងនេះជា​ផ្នែកនៃបំណាត់ការអភិវឌ្ឍថ្មីរបស់អ្នក។
- កម្មវិធីនេះមានតែARM ប៉ុណ្ណោះ: តាមដានវិធីសាស្រ្ត
  [ការត្រួតពិនិត្យនិងការសម្អាត](retail-multiagent-arm-template/README.md)។
  `azd down` មិនគ្រប់គ្រងធនធានទាំងនោះទេ។
