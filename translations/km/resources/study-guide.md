## ការណែនាំ

មគ្គុទេសក៍សិក្សាទាំងមូលនេះផ្តល់ជូនគោលបំណងការសិក្សាផ្គុំមានរចនាសម្ព័ន្ធ។ មានមាតិកាសំខាន់ៗ, ផលិតការអនុវត្តន៍និងសម្ភាសន៍តាមការវាយតម្លៃ ដើម្បីជួយអ្នកចេះជំនាញក្នុង Azure Developer CLI (azd) ដោយប្រើមគ្គុទេសក៍នេះ ដើម្បីតាមដាននិងធ្វើឲ្យប្រាកដថាអ្នកបានគ្របដណ្តប់គ្រប់ប្រធានបទសំខាន់ៗហើយ។

## គោលបំណងការសិក្សា

ដោយបញ្ចប់មគ្គុទេសក៍សិក្សានេះ អ្នកនឹង៖
- ជំនាញឯកទេសលើគំនិតមូលដ្ឋាន និងជំនាញកម្រិតខ្ពស់របស់ Azure Developer CLI
- អភិវឌ្ឍជំនាញអនុវត្តន៍ក្នុងការផ្គត់ផ្គង់និងគ្រប់គ្រងកម្មវិធី Azure
- បង្កើតកម្រិតទំនុកចិត្តក្នុងការដោះស្រាយបញ្ហា និងបង្កើនប្រសិទ្ធភាពនៃការផ្គត់ផ្គង់កម្មវិធី
- យល់ដឹងអំពីបច្ចេកទេសផ្គត់ផ្គង់នៅជំហានផលិតកម្ម និងវិចារណករណីសុវត្ថិភាព

## លទ្ធផលនៃការសិក្សា

បន្ទាប់ពីបញ្ចប់គ្រប់ផ្នែកនៃមគ្គុទេសក៍នេះ អ្នកនឹងអាច៖
- រចនារចនាសម្ព័ន្ធការដាក់កម្មវិធីពេញលេញដោយប្រើ azd
- អនុវត្តយុទ្ធសាស្ត្រត្រួតពិនិត្យបន្តបន្ទាប់ សុវត្ថិភាព និងបង្កើតចំណាយកាត់បន្ថយ
- ដោះស្រាយបញ្ហាការផ្គត់ផ្គង់ស្មុគស្មាញដោយឯករាជ្យ
- បង្កើតទំព័រឯកសារប្រភេទតាមបំណង និងរួមចំណែកក្នុងសហគមន៍ azd

## រចនាសម្ព័ន្ធការសិក្សា 8 ជំពូក

### ជំពូក 1: មូលដ្ឋាន និងចាប់ផ្តើមយ៉ាងរហ័ស (សប្តាហ៍ 1)
**រយៈពេល**៖ 30-45 នាទី | **កម្រិតស្មុគស្មាញ**: ⭐

#### គោលបំណងការសិក្សា
- យល់ដឹងពីគំនិតមូលដ្ឋាននៃ Azure Developer CLI និងពាក្យបរិយាយ
- ដំឡើង និងកំណត់រចនាសម្ព័ន្ធ AZD លើវេទិកាការអភិវឌ្ឍរបស់អ្នកដោយជោគជ័យ
- ផ្គត់ផ្គង់កម្មវិធីដំបូងរបស់អ្នកដោយប្រើទំព័រគំរូដែលមានស្រាប់
- ចូលរួម គ្រប់គ្រងកម្មវិធី AZD បានយ៉ាងមានប្រសិទ្ធភាព

#### គំនិតសំខាន់ៗដែលត្រូវគ្រប់គ្រង
- រចនាសម្ព័ន្ធ និងសមាសធាតុគម្រោង AZD (azure.yaml, infra/, src/)
- ដំណើរការផ្គត់ផ្គង់ដោយប្រើទំព័រគំរូ
- មូលដ្ឋានការកំណត់បរិយាកាស
- ការគ្រប់គ្រងក្រុមធនធាន និងការជាវចុះតាម

#### ការអនុវត្តន៍
1. **ការត្រួតពិនិត្យការដំឡើង**៖ ដំឡើង AZD និងពិនិត្យដោយ `azd version`
2. **ការផ្គត់ផ្គង់ដំបូង**៖ ផ្គត់ផ្គង់ទំព័រគំរូ todo-nodejs-mongo ជា​ដំណើរការ​ជោគជ័យ
3. **ការកំណត់បរិយាកាស**៖ កំណត់អថេរបរិយាកាសដំបូងរបស់អ្នក
4. **ការរុករកធនធាន**៖ រុករកធនធានដែលបានផ្គត់ផ្គង់នៅក្នុង Azure Portal

#### សំណួរវាយតម្លៃ
- តើសមាសធាតុលប្បយស្នូលនៃគម្រោង AZD មានអ្វីខ្លះ?
- តើអ្នកចាប់ផ្តើមគម្រោងថ្មីពីទំព័រគំរូយ៉ាងដូចម្តេច?
- តើតម្លេខុសគ្នារវាង `azd up` និង `azd deploy` ជាអ្វី?
- តើអ្នកគ្រប់គ្រងបរិយាកាសច្រើនជាមួយ AZD យ៉ាងដូចម្តេច?

### ជំពូក 2: ការអភិវឌ្ឍ AI ជាមុន (សប្តាហ៍ 2)
**រយៈពេល**៖ 1-2 ម៉ោង | **កម្រិតស្មុគស្មាញ**: ⭐⭐

#### គោលបំណងការសិក្សា
- បញ្ចូលសេវាកម្ម Microsoft Foundry ជាមួយដំណើរការ AZD
- ផ្គត់ផ្គង់ និងកំណត់រចនាសម្ព័ន្ធកម្មវិធីដែលមាន AI ជំនួយ
- យល់ដឹងពីលំនាំអនុវត្តក RAG (Retrieval-Augmented Generation)
- គ្រប់គ្រងការផ្គត់ផ្គង់និងតម្រូវទំហំម៉ូដែល AI

#### គំនិតសំខាន់ៗដែលត្រូវគ្រប់គ្រង
- ការបញ្ចូលសេវាកម្ម Microsoft Foundry Models និងការគ្រប់គ្រង API
- ការកំណត់រចនាសម្ព័ន្ធ AI Search និងវិធីសាស្រ្តសន្ទស្សន៍វ៉ិចទ័រ
- យុទ្ធសាស្ត្រផ្គត់ផ្គង់ម៉ូដែល និងការធ្វើផែនការកំណត់ទំហំ
- ការត្រួតពិនិត្យកម្មវិធី AI និងការបង្កើនប្រសិទ្ធភាព

#### ការអនុវត្តន៍
1. **ការផ្គត់ផ្គង់ AI Chat**៖ ផ្គត់ផ្គង់ទំព័រគំរូ azure-search-openai-demo
2. **អនុវត្ត RAG**៖ កំណត់ឯកសារសន្ទស្សនា និងការទាញយក
3. **ការកំណត់ម៉ូដែល**៖ បង្កើតម៉ូដែល AI ច្រើនគោលបំណងខុសៗគ្នា
4. **ត្រួតពិនិត្យ AI**៖ អនុវត្ត Application Insights សម្រាប់ការប្រតិបត្តិការរបស់ AI

#### សំណួរវាយតម្លៃ
- តើអ្នកកំណត់រចនាសម្ព័ន្ធសេវាកម្ម Microsoft Foundry Models ក្នុងទំព័រគំរូ AZD បានយ៉ាងដូចម្តេច?
- តើសមាសធាតុសំខាន់ៗរបស់​រចនាសម្ព័ន្ធ RAG មានអ្វីខ្លះ?
- តើអ្នកគ្រប់គ្រងទំហំ និងការធ្វើបែបផែនម៉ូដែល AI យ៉ាងដូចម្តេច?
- តើគោលបំណងត្រួតពិនិត្យណាមួយសំខាន់សម្រាប់កម្មវិធី AI?

### ជំពូក 3: ការកំណត់រចនាសម្ព័ន្ធ និងការផ្ទៀងផ្ទាត់សុវត្ថិភាព (សប្តាហ៍ 3)
**រយៈពេល**: 45-60 នាទី | **កម្រិតស្មុគស្មាញ**: ⭐⭐

#### គោលបំណងការសិក្សា
- ជំនាញទាក់ទងនឹងការគ្រប់គ្រង និងការកំណត់រចនាសម្ព័ន្ធបរិយាកាស
- អនុវត្តគំរូសុវត្ថិភាព និងការផ្ទៀងផ្ទាត់ managed identity
- រៀបចំធនធានដោយប្រើលក្ខណៈ​ឈ្មោះ​គោលលក្ខណៈត្រឹមត្រូវ
- កំណត់រចនាសម្ព័ន្ធការផ្គត់ផ្គង់នៅបរិយាកាសច្រើន (dev, staging, prod)

#### គំនិតសំខាន់ៗដែលត្រូវគ្រប់គ្រង
- អថេរបរិយាកាសស្រទាប់ និងអាទិភាពកំណត់រចនាសម្ព័ន្ធ
- ផ្ទៀងផ្ទាត់ managed identity និង service principal
- បញ្ចូល Key Vault សម្រាប់គ្រប់គ្រងឯកសារល្ងង់
- ការគ្រប់គ្រងប៉ារ៉ា៉មែត្រ​ផ្លែកៗតាមបរិយាកាស

#### ការអនុវត្តន៍
1. **ការកំណត់បរិយាកាសច្រើន**៖ កំណត់រចនាសម្ព័ន្ធ dev, staging, និង prod
2. **កំណត់សុវត្ថិភាព**៖ អនុវត្តការផ្ទៀងផ្ទាត់ managed identity
3. **គ្រប់គ្រងឯកសារ​ល្ងង់**៖ បញ្ចូល Azure Key Vault សម្រាប់ទិន្នន័យសំខាន់
4. **ការគ្រប់គ្រងប៉ារ៉ាមែត្រ**៖ បង្កើតរចនាសម្ព័ន្ធដែលផ្លែកគ្នាតាមបរិយាកាស

#### សំណួរវាយតម្លៃ
- តើអ្នកកំណត់រចនាសម្ព័ន្ធបរិយាកាសខុសៗគ្នាជាមួយ AZD របៀបណា?
- តើអត្ថប្រយោជន៍នៃ managed identity ជាង service principals មានអ្វីខ្លះ?
- តើអ្នកគ្រប់គ្រងឯកសារល្ងង់កម្មវិធីយ៉ាងដូចម្តេច?
- តើរបៀបកំណត់រចនាសម្ព័ន្ធនៅ AZD មានលំដាប់យ៉ាងដូចម្តេច?

- យល់ដឹងពីយុទ្ធសាស្ត្រចែកចាយធនធាន

#### គំនិតសំខាន់ៗដែលត្រូវគ្រប់គ្រង

- យុទ្ធសាស្ត្រពាក់ព័ន្ធធនធាន និងលំដាប់ផ្គត់ផ្គង់
- ការប្រើប្រាស់ឯកសារប៉ារ៉ាមែត្រ និងមូឌុលទំព័រគំរូ
- ការបង្កើត hook ផ្ទាល់ខ្លួន និងស្វ័យប្រវត្តិការ​ផ្គត់ផ្គង់
- លំនាំផ្គត់ផ្គង់កម្មវិធី container (ចាប់ផ្តើមរហ័ស, ផលិតកម្ម, មីក្រូសេវា)

3. **ស្វ័យប្រវត្តិការ​ផ្គត់ផ្គង់**៖ អនុវត្ត hook មុន/ក្រោយការផ្គត់ផ្គង់
4. **រចនាសម្ព័ន្ធ​ស្ថាបត្យកម្ម**៖ ផ្គត់ផ្គង់រចនាសម្ព័ន្ធមីក្រូសេវាចម្ងាយ
5. **ការផ្គត់ផ្គង់ container app**៖ ផ្គត់ផ្គង់គំរូ [Simple Flask API](../../../examples/container-app/simple-flask-api) និង [Microservices Architecture](../../../examples/container-app/microservices) តាមរយៈ AZD

- តើយ៉ាងដូចម្តេចដែលអ្នកដោះស្រាយលំដាប់ធនធានក្នុងទំព័រគំរូ?
- តើលំនាំផ្សាយបន្តផ្ទាល់បានគាំទ្រឲ្យធ្វើបច្ចុប្បន្នភាពដោយមិនបាត់បង់សេវាកម្មមានអ្វីខ្លះ?

### ជំពូក 5: ដំណោះស្រាយ AI ប្រភេទ multi-agent (សប្តាហ៍ 6-7)
**រយៈពេល**: 2-3 ម៉ោង | **កម្រិតស្មុគស្មាញ**: ⭐⭐⭐⭐

#### គោលបំណងការសិក្សា
- រចនា និងអនុវត្តរចនាសម្ព័ន្ធ multi-agent AI
- សម្របសម្រួលសម្រង់និងការសារព័ត៌មានរបស់ភាគី
- ផ្គត់ផ្គង់ដំណោះស្រាយ AI ជាជំហានផលិតកម្មជាមួយការត្រួតពិនិត្យ
- យល់ដឹងពីជំនាញពិសេសរបស់ភាគី និងលំនាំដំណើរការ
- បញ្ចូលមីក្រូសេវាកម្ម container ក្នុងដំណោះស្រាយ multi-agent

#### គំនិតសំខាន់ៗដែលត្រូវគ្រប់គ្រង
- លំនាំរចនាសម្ព័ន្ធ multi-agent និងគោលការណ៍រចនា
- ពិធីសាស្ត្រសារព័ត៌មានភាគី និងការបញ្ជូនទិន្នន័យ
- លំនាំបែងចែក និងតម្រូវទំហំសម្រាប់ភាគី AI
- ការត្រួតពិនិត្យផលិតកម្មសម្រាប់ប្រព័ន្ធ multi-agent
- សារព័ត៌មានសេវាកម្មទៅសេវាកម្មក្នុងបរិយាកាស containerized

#### ការអនុវត្តន៍
1. **សមិទ្ធផលរចនាសម្ព័ន្ធ Retail**: វិភាគផែនការលំអិតនៃលំនាំលក់ និងសម្គាល់ថា ធាតុកម្មវិធីណាដែលត្រូវអនុវត្តមុនការផ្គត់ផ្គង់
2. **ប្ដូរប្រព័ន្ធភាគី**: ប្ដូរប្រព័ន្ធរបស់ភាគី Customer និង Inventory
3. **បចេ្តកំរិតរចនាសម្ព័ន្ធ**: អនុវត្តបែងចែក និងបង្កើនទំហំដោយស្វ័យប្រវត្តិ
4. **ការត្រួតពិនិត្យផលិតកម្ម**: កំណត់ការត្រួតពិនិត្យនិងការជូនដំណឹង​យ៉ាងទូលំទូលាយ
5. **បញ្ចូលមីក្រូសេវាកម្ម**: ពង្រីកគំរូ [Microservices Architecture](../../../examples/container-app/microservices) ដើម្បីគាំទ្រការដំណើរការជាមួយភាគី

#### សំណួរវាយតម្លៃ
- តើយ៉ាងដូចម្តេចដែលអ្នករចនាលំនាំសារព័ត៌មាន multi-agent ដើម្បីដំណើរការ​បានប្រសើរជាង?
- តើកត្តាសំខាន់ៗសម្រាប់ការធ្វើបែបផែនទំហំ និងបែងចែកភារកិច្ច AI agent មានអ្វីខ្លះ?
- តើអ្នកត្រួតពិនិត្យ និងដោះស្រាយបញ្ហាប្រព័ន្ធ multi-agent AI យ៉ាងដូចម្តេច?
- តើលំនាំផលិតកម្មណាដែលធានាបានពីសុវត្ថិភាពសម្រាប់ភាគី AI?

### ជំពូក 6: ការត្រួតពិនិត្យមុនការផ្គត់ផ្គង់ និងការធ្វើផែនការ (សប្តាហ៍ 8)
**រយៈពេល**: 1 ម៉ោង | **កម្រិតស្មុគស្មាញ**: ⭐⭐

- ជ្រើសរើស SKU Azure យ៉ាងត្រឹមត្រូវសម្រាប់ការកាត់បន្ថយចំណាយ
- អនុវត្តការត្រួតពិនិត្យមុនការផ្គត់ផ្គង់ដោយស្វ័យប្រវត្តិ
- ធ្វើផែនការផ្គត់ផ្គង់ដោយយុទ្ធសាស្ត្រកាត់បន្ថយចំណាយ

#### គំនិតសំខាន់ៗដែលត្រូវគ្រប់គ្រង

- ការជ្រើសរើស SKU និងការកាត់បន្ថយចំណាយ
- សៀវភៅអូតូម៉ាទិក និងការធ្វើតេស្ត
- ផែនការផ្គត់ផ្គង់ និងការវាយតម្លៃហានិភ័យ

#### ការអនុវត្តន៍
1. **វិភាគថាមពល**: វិភាគតម្រូវការធនធានសម្រាប់កម្មវិធីរបស់អ្នក

3. **ស្វ័យប្រវត្តិកាត់បន្ថយការត្រួតពិនិត្យ**: អនុវត្តស្គ្រីបត្រួតពិនិត្យមុនការផ្គត់ផ្គង់
4. **ការធ្វើផែនការចំណាយ**: បង្កើតការរំពឹងចំណាយនិងថវិកាផ្គត់ផ្គង់

- តើអ្នកដំណើរការស្វ័យប្រវត្តិការត្រួតពិនិត្យមុនការផ្គត់ផ្គង់យ៉ាងដូចម្តេច?
- តើយុទ្ធសាស្ត្រអ្វីខ្លះជួយបង្កើនប្រសិទ្ធភាពចំណាយផ្គត់ផ្គង់?

- គ្រប់គ្រងបញ្ហាពិសេស AI និងបញ្ហាបង្កើនប្រសិទ្ធភាព

- ស្កេម៉ាសម្រាប់មូលដ្ឋានទិន្នន័យ និងស្គ្រីបផ្លាស់ប្តូរ
- ផ្ទាំងត្រួតពិនិត្យ និងច្បាប់ព្រមាន
- ការកំណត់ការចុះផ្សាយតាមបរិយាកាសច្រើន

### គម្រោង 3: វេទិការជួញដូរ E-commerce ប្រើ Microservices
**កម្រិតកំហុស**: កម្រិតខ្ពស់  
**រយៈពេល**: 4-6 សប្តាហ៍

រចនា និងអនុវត្តវេទិកាជួញដូរទំនិញប្រើ Microservices:
- សេវាកម្ម API ជាច្រើន (បញ្ជីទំនិញ, អរយ៉ាត់, ការទូទាត់, អ្នកប្រើប្រាស់)
- រួមបញ្ចូលមុខដំណើរការសារជាមួយ Service Bus
- ការប្រើ Redis cache សម្រាប់បង្កើនប្រសិទ្ធិភាព
- ការចុះកំណត់ហេតុ និងត្រួតពិនិត្យយ៉ាងទូលំទូលាយ

**ឧទាហរណ៍យោង**: សូមមើល [Microservices Architecture](../../../examples/container-app/microservices) សម្រាប់គំរូការសិក្សាពីសេវាកម្មពីរនិងមគ្គុទេសក៍ចុះផ្សាយ។ របាំងសារ, សុពលភាព, ការផ្ទៀងផ្ទាត់, ដំណើរការទូទាត់, និងការប្រជុំផលិតកម្មគឺជាការងារដាច់ដោយឡែក។

**របស់ដែលត្រូវដាក់ស្នើ**:
- រចនាសម្ព័ន្ធ Microservices ពេញលេញ
- លំនាំការទំនាក់ទំនងរវាងសេវាកម្ម
- ការធ្វើតេស្តប្រសិទ្ធភាព និងបង្កើនប្រសិទ្ធភាព
- ការអនុវត្តសុវត្ថិភាពរួចរាល់សម្រាប់ផលិតកម្ម

ធ្វើការវាយតម្លៃទាំងនេះបន្ទាប់ពីមូឌុលនីមួយៗ៖

**ការវាយតម្លៃមូឌុល 1**: គំនិតមូលដ្ឋាន និងការដំឡើង
- សំណួរជាច្រើនជម្រើសលើគំនិតសំខាន់ៗ
- ការអនុវត្តដំឡើង និងកំណត់រចនាសម្ព័ន្ធ
- សមរាជ្យចុះផ្សាយសាមញ្ញ

**ការវាយតម្លៃមូឌុល 2**: ការកំណត់រចនាសម្ព័ន្ធ និងបរិយាកាស
- ស្ថានការណ៍គ្រប់គ្រងបរិយាកាស
- សមរាជ្យដោះស្រាយបញ្ហាការកំណត់រចនាសម្ព័ន្ធ
- ការអនុវត្តសុវត្ថិភាព

**ការវាយតម្លៃមូឌុល 3**: ចុះផ្សាយ និងផ្គត់ផ្គង់ធនធាន
- បញ្ហារចនាសម្ព័ន្ធហេដ្ឋារចនាសម្ព័ន្ធ
- ស្ថានការណ៍ចុះផ្សាយសេវាកម្មជាច្រើន
- សមរាជ្យបង្កើនប្រសិទ្ធភាព

**ការវាយតម្លៃមូឌុល 4**: ត្រួតពិនិត្យមុនចុះផ្សាយ
- ករណីផែនការសមត្ថភាព
- ស្ថានការណ៍បង្កើនប្រសិទ្ធភាពថ្លៃដើម
- ការអនុវត្តបណ្តាញផ្លូវត្រួតពិនិត្យ

**ការវាយតម្លៃមូឌុល 5**: ដោះស្រាយបញ្ហា និងជួសជុលកូដ
- សមរាជ្យរោគសញ្ញាបញ្ហា
- ការអនុវត្តការត្រួតពិនិត្យ
- ការចូលរួមប្រតិកម្មហេតុការណ៍

**ការវាយតម្លៃមូឌុល 6**: ប្រធានបទកម្រិតខ្ពស់
- ការរចនាបណ្តាញផ្លូវ CI/CD
- ការអភិវឌ្ឍទំព័រគំរូផ្ទាល់ខ្លួន
- ស្ថានការណ៍ស្ថាបត្យកម្មសហគ្រាស

**ក្រមវាយតម្លៃ**:

- ការអនុលោមសុវត្ថិភាព និងវិធីសាស្រ្តល្អបំផុត
- ការបង្កើនប្រសិទ្ធភាព និងថ្លៃដើម
- ប្រសិទ្ធភាពការដោះស្រាយបញ្ហា និងការត្រួតពិនិត្យ

- **ការត្រួតពិនិត្យសុវត្ថិភាព**: ឯកសារត្រួតពិនិត្យ និងចន្លោះសុវត្ថិភាពដែលនៅសល់ ទៅតាមតម្រូវការរបស់អង្គភាពរបស់អ្នក; ការសម្រេចបញ្ចប់វគ្គមិនមែនជារូបមន្តធានាស្របច្បាប់
