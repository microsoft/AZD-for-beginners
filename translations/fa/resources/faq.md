## شروع به کار

### س: Azure Developer CLI (azd) چیست؟
**ج**: Azure Developer CLI (azd) یک ابزار خط فرمان متمرکز بر توسعه‌دهنده است که زمان لازم برای انتقال برنامه شما از محیط توسعه محلی به Azure را تسریع می‌کند. این ابزار بهترین شیوه‌ها را از طریق قالب‌ها ارائه می‌دهد و به کل چرخه عمر استقرار کمک می‌کند.

### س: azd چگونه با Azure CLI متفاوت است؟
**ج**: 
- **Azure CLI**: ابزار عمومی برای مدیریت منابع Azure
- **azd**: ابزاری متمرکز بر توسعه‌دهنده برای روندهای کار استقرار برنامه‌ها
- azd روند احراز هویت و استقرار خود را دارد؛ Azure CLI ابزاری جداگانه و مکمل است
- azd شامل قالب‌ها، مدیریت محیط و اتوماسیون استقرار است

### س: آیا برای استفاده از azd باید Azure CLI نصب کرده باشم؟
**ج**: برای روند کاری اصلی AZD نیاز نیست. با `azd auth login` احراز هویت کنید. هنگامی که یک قلاب قالب یا تمرین صریحا دستورات `az` را اجرا می‌کند، Azure CLI را جداگانه نصب کنید.

### س: azd از چه زبان‌های برنامه‌نویسی پشتیبانی می‌کند؟
**ج**: azd زبان‌-بی‌طرف است. این ابزار با موارد زیر کار می‌کند:
- Node.js/JavaScript/TypeScript
- Python
- .NET/C#
- Java
- Go
- PHP
- وب‌سایت‌های استاتیک
- برنامه‌های کانتینریزه‌شده

### س: آیا می‌توانم azd را با پروژه‌های موجود استفاده کنم؟
**ج**: بله! شما می‌توانید یا:
1. از `azd init` برای افزودن پیکربندی azd به پروژه‌های موجود استفاده کنید
2. پروژه‌های موجود را با ساختار قالب azd تطبیق دهید
3. قالب‌های سفارشی بر اساس معماری موجود خود ایجاد کنید

### س: با در دسترس بودن کلی افزونه Foundry چه تغییراتی رخ داده است؟
**ج**: بسته `microsoft.foundry` به نسخه ۱.۰ و GA در ۵ نوامبر ۲۰۲۶ رسید. با AZD 1.37.0+ از `azd ext install microsoft.foundry` برای نصب هفت افزونه اصلی برای عوامل، اتصال‌ها، بازرس، پروژه‌ها، رویه‌ها، مهارت‌ها و جعبه ابزارها استفاده کنید. این یک فضای نام دستوری جدید نیست، و اجزای آن مستقل از هم نسخه‌بندی می‌شوند. ارزیابی‌ها، داده‌ها، تنظیم دقیق و مدل‌های سفارشی به طور جداگانه نصب می‌شوند؛ ویژگی‌های پیش‌نمایش اختیاری صرفا به دلیل GA شدن بسته GA نمی‌شوند.

راهنمای گام به گام [hosted-agent](../docs/chapter-02-ai-development/microsoft-foundry-integration.md#hosted-agent-walkthrough-ga) از Python 3.13+ و uv فعلی استفاده می‌کند. `azd ai agent run` بازرس عامل را به صورت محلی باز می‌کند، اما فراخوانی مدل‌ها همچنان از Azure استفاده کرده و هزینه‌ها را به دنبال دارد. حالت کد `azd deploy` منبع را برای یک ساخت از راه دور آپلود می‌کند بدون اینکه لازم باشد ساخت محلی کانتینر انجام شود.

### س: آیا `azd down` یک عامل میزبانی‌شده را از پروژه Foundry موجود حذف می‌کند؟
**ج**: در مسیر پروژه استفاده‌شده که در راه‌اندازی سریع عامل میزبانی‌شده توصیف شده، خیر: این پروژه، عامل میزبانی‌شده و منابع دیگر را نگه می‌دارد. منابع ناخواسته را جداگانه حذف کنید بدون اینکه منابع مشترک حذف شوند. اگر محیط یک پروژه Foundry جدید ایجاد کرده باشد، `azd down` گروه منابع آن را به همراه همه محتویاتش حذف می‌کند. پیش از تأیید، راهنمایی‌های [پاک‌سازی](../docs/chapter-02-ai-development/microsoft-foundry-integration.md#7-clean-up-deliberately) و پیام‌های حذف را مرور کنید.

## احراز هویت و دسترسی

### س: چگونه با استفاده از azd به Azure احراز هویت کنم؟
**ج**: از `azd auth login` استفاده کنید که یک پنجره مرورگر برای احراز هویت Azure باز می‌کند. برای سناریوهای CI/CD از Service Principal یا managed identity استفاده کنید.

### س: آیا می‌توانم azd را با چند اشتراک Azure استفاده کنم؟
**ج**: بله. برای هر محیط از `azd env set AZURE_SUBSCRIPTION_ID <subscription-id>` برای مشخص کردن اشتراک مورد استفاده استفاده کنید.

### س: چه دسترسی‌هایی برای استقرار با azd نیاز دارم؟
**ج**: معمولاً نیاز دارید به:
- نقش **Contributor** در گروه منابع یا اشتراک
- نقش **User Access Administrator** اگر منابعی استقرار دهید که نیاز به تخصیص نقش دارند
- دسترسی‌های خاص بستگی به قالب و منابعی دارد که استقرار می‌دهید

### س: آیا می‌توانم azd را در خطوط لوله CI/CD استفاده کنم؟
**ج**: قطعاً! azd برای ادغام با CI/CD طراحی شده است. احراز هویت را با service principal انجام دهید و متغیرهای محیطی را برای پیکربندی تنظیم کنید.

### س: چگونه در GitHub Actions احراز هویت را انجام دهم؟
**ج**: ترجیحاً از federation هویت بار کاری (OIDC) استفاده کنید که با `azd pipeline config` پیکربندی می‌شود. روند کاری ایجاد شده AZD را نصب می‌کند و AZD را مستقیماً با هویت متصل شده احراز هویت می‌کند. صرف یک مرحله `azure/login` ورود به AZD ایجاد نمی‌کند. یک مرحله ورود درون یک کار موجود به شکل زیر است:
```yaml
permissions:
  contents: read
  id-token: write
steps:
  - uses: actions/checkout@v7
  - uses: Azure/setup-azd@v2
  - run: >-
      azd auth login
      --client-id "${{ vars.AZURE_CLIENT_ID }}"
      --tenant-id "${{ vars.AZURE_TENANT_ID }}"
      --federated-credential-provider github
```

پس از ورود، با محیط AZD، اشتراک و موقعیت مورد نظر اقدام به ایجاد یا استقرار کنید. اعتبار تجمیعی هویت باید مخزن/ref روند کاری یا محیط GitHub را مورد اعتماد قرار دهد و نقش‌های Azure آن باید عملیات درخواستی را مجاز کند.

## قالب‌ها و پروژه‌ها

### س: قالب‌های azd را کجا می‌توانم پیدا کنم؟
**ج**: 
- قالب‌های رسمی و جامعه: [Awesome AZD](https://azure.github.io/awesome-azd/)
- قالب‌های جامعه: جستجو در GitHub برای "azd-template"
- از `azd template list` برای مرور قالب‌های موجود استفاده کنید

### س: چگونه قالب سفارشی بسازم؟
**ج**: 
1. با ساختار قالب موجود شروع کنید
2. `azure.yaml`، فایل‌های زیرساخت و کد برنامه را تغییر دهید
3. به طور کامل با `azd up` آزمایش کنید
4. با برچسب‌های مناسب در GitHub منتشر کنید

### س: آیا می‌توانم بدون قالب از azd استفاده کنم؟
**ج**: بله، از `azd init` در یک پروژه موجود برای ایجاد فایل‌های پیکربندی لازم استفاده کنید. باید به صورت دستی `azure.yaml` و فایل‌های زیرساخت را پیکربندی کنید.

### س: تفاوت قالب‌های رسمی با قالب‌های جامعه چیست؟
**ج**: 
- **قالب‌های رسمی**: توسط مایکروسافت نگهداری می‌شوند، به طور منظم به‌روزرسانی شده، مستندسازی جامع دارند
- **قالب‌های جامعه**: توسط توسعه‌دهندگان ساخته شده‌اند، ممکن است موارد استفاده تخصصی داشته باشند، کیفیت و نگهداری متفاوت دارند

### س: چگونه قالب پروژه را به‌روزرسانی کنم؟
**ج**: قالب‌ها به طور خودکار به‌روزرسانی نمی‌شوند. شما می‌توانید:
1. تغییرات منبع قالب را به صورت دستی مقایسه و ادغام کنید
2. تازه شروع کنید با `azd init` با استفاده از قالب به‌روزشده
3. به صورت انتخابی بهبودهای خاصی را از قالب‌های به‌روزشده بردارید

## استقرار و زیرساخت

### س: azd چه خدمات Azure را می‌تواند مستقر کند؟
**ج**: azd می‌تواند هر سرویس Azure را از طریق قالب‌های Bicep/ARM مستقر کند، شامل:
- خدمات اپلیکیشن، برنامه‌های کانتینری، عملکردها
- پایگاه‌های داده (SQL، PostgreSQL، Cosmos DB)
- ذخیره‌سازی، Key Vault، Application Insights
- شبکه، امنیت و منابع مانیتورینگ

### س: آیا می‌توانم به چند منطقه استقرار انجام دهم؟
**ج**: بله، چند منطقه را در قالب‌های Bicep خود پیکربندی کرده و پارامتر موقعیت را به طور مناسب برای هر محیط تنظیم کنید.

### س: چگونه مهاجرت‌های طرح پایگاه داده را مدیریت کنم؟
**ج**: از قلاب‌های استقرار در `azure.yaml` استفاده کنید:
```yaml
hooks:
  postdeploy:
    posix:
      run: ./scripts/migrate-database.sh
    windows:
      run: ./scripts/migrate-database.ps1
```

### س: آیا می‌توانم فقط زیرساخت را بدون برنامه‌ها مستقر کنم؟
**ج**: بله، از `azd provision` برای استقرار فقط مؤلفه‌های زیرساخت تعریف شده در قالب‌هایتان استفاده کنید.

### س: چگونه به منابع Azure موجود استقرار دهم؟
**ج**: بله، زمانی که قالب پشتیبانی کند. منابع موجود را با اعلامیه‌های `existing` بایسپ یا پارامترهای مستند شده منابع موجود قالب ارجاع دهید، و خدمات برنامه را به اهداف مورد نظرشان نقشه کنید. این مالکیت را وارد نمی‌کند و به طور خودکار مجوزهای گمشده ایجاد نمی‌کند. پیش از استقرار قالب را مرور کنید.

### س: آیا می‌توانم به جای Bicep از Terraform استفاده کنم؟
**ج**: بله. AZD از Terraform و Bicep پشتیبانی می‌کند. قالب مبتنی بر Terraform را انتخاب کنید یا `infra.provider: terraform` را در `azure.yaml` پیکربندی کنید، به همراه فایل‌های لازم Terraform و پیکربندی state/backend مناسب. راهنمای [روند کاری Terraform](https://learn.microsoft.com/azure/developer/azure-developer-cli/use-terraform-for-azd) را ببینید.

## پیکربندی و محیط‌ها

### س: چگونه محیط‌های مختلف (dev، staging، prod) را مدیریت کنم؟
**ج**: با `azd env new <environment-name>` محیط‌های جداگانه ایجاد کنید و پیکربندی‌های مختلفی برای هرکدام تنظیم کنید:
```bash
azd env new development
azd env new staging  
azd env new production
```

### س: پیکربندی‌های محیط در کجا ذخیره می‌شوند؟
**ج**: در پوشه `.azure` در دایرکتوری پروژه شما. هر محیط پوشه مخصوص به خود را با فایل‌های پیکربندی دارد.

### س: چگونه پیکربندی مخصوص محیط را تنظیم کنم؟
**ج**: برای تنظیم متغیرهای محیط از `azd env set` استفاده کنید:
```bash
azd env set AZURE_LOCATION eastus
azd env set DATABASE_TIER Basic
```

### س: آیا می‌توانم پیکربندی محیط‌ها را بین اعضای تیم به اشتراک بگذارم؟
**ج**: پوشه `.azure` حاوی اطلاعات حساس است و نباید به کنترل نسخه ارسال شود. در عوض:
1. متغیرهای محیط مورد نیاز را مستندسازی کنید
2. از اسکریپت‌های استقرار برای راه‌اندازی محیط‌ها استفاده کنید
3. برای پیکربندی حساس از Azure Key Vault استفاده کنید

### س: چگونه مقادیر پیش‌فرض قالب را بازنویسی کنم؟
**ج**: متغیرهای محیط را که متناظر پارامترهای قالب هستند تنظیم کنید:
```bash
azd env set AZURE_LOCATION westus2
azd env set SKU_NAME "B1"
```

تنها متغیرهایی که توسط قالب مصرف می‌شوند بر استقرار تأثیر می‌گذارند. `SKU_NAME` بالا نمونه یک ورودی سفارشی است، نه یک تنظیم عمومی AZD.

## عیب‌یابی

### س: چرا `azd up` شکست می‌خورد؟
**ج**: علل رایج:
1. **مشکلات احراز هویت**: اجرای `azd auth login`
2. **دسترسی‌های ناکافی**: اختصاص نقش‌های Azure خود را بررسی کنید
3. **تداخل نام منابع**: منابع متداخل و ورودی‌های نام قالب را بررسی کنید؛ هنگام نیاز به ایزوله کردن، با `azd env new` محیط جداگانه ایجاد کنید
4. **مشکلات سهمیه/ظرفیت**: دسترسی منطقه‌ای را بررسی کنید
5. **خطاهای قالب**: قالب‌های Bicep را اعتبارسنجی کنید

### س: چگونه اشکال‌زدایی شکست‌های استقرار را انجام دهم؟
**ج**: 
1. از `azd deploy --debug` برای خروجی دقیق استفاده کنید
2. تاریخچه استقرار در پرتال Azure را بررسی کنید
3. گزارش فعالیت در پرتال Azure را مرور کنید
4. با `azd show` وضعیت محیط فعلی را نمایش دهید

### س: چرا متغیرهای محیط من کار نمی‌کنند؟
**ج**: بررسی کنید:
1. نام متغیرها دقیقاً مطابق پارامترهای قالب باشد
2. اگر مقدار حاوی فاصله است، به درستی داخل کوتیشن قرار گرفته باشد
3. محیط انتخاب شده باشد: `azd env select <environment>`
4. متغیرها در محیط صحیح تنظیم شده باشند

### س: چگونه استقرارهای ناموفق را پاک‌سازی کنم؟
**ج**: 
```bash
azd down
```
 ابتدا محیط انتخاب شده و تأیید حذف را بررسی کنید. این عمل منابع Azure تأمین شده را حذف می‌کند، اما پیکربندی محیط محلی `.azure` را حذف نمی‌کند. `--purge` علاوه بر این درخواست حذف دائم منابع نرم‌حذف شده پشتیبانی شده را می‌کند و ممکن است توسط حفاظت نگهداری/پاک‌سازی مسدود شود؛ این یک مرحله بازیابی معمولی نیست.

### س: چرا برنامه من پس از استقرار قابل دسترس نیست؟
**ج**: بررسی کنید:
1. استقرار با موفقیت انجام شده است
2. برنامه در حال اجرا است (لاگ‌ها در پرتال Azure را بررسی کنید)
3. گروه‌های امنیت شبکه اجازه ترافیک را می‌دهند
4. دامنه‌های DNS/سفارشی به درستی پیکربندی شده‌اند

## هزینه و صورتحساب

### س: استقرارهای azd چقدر هزینه خواهد داشت؟
**ج**: هزینه‌ها بستگی دارد به:
- خدمات Azure مستقر شده
- سطوح خدمات/SKUهای انتخاب شده
- تفاوت قیمت‌های منطقه‌ای
- الگوهای مصرف

از [ماشین حساب قیمت‌گذاری Azure](https://azure.microsoft.com/pricing/calculator/) برای برآوردها استفاده کنید.

### س: چگونه هزینه‌ها را در استقرارهای azd کنترل کنم؟
**ج**: 
1. برای محیط‌های توسعه از SKUهای سطح پایین‌تر استفاده کنید
2. بودجه‌ها و هشدارهای Azure را تنظیم کنید
3. برای حذف منابع زمانی که نیاز نیست از `azd down` استفاده کنید
4. مناطق مناسب را انتخاب کنید (هزینه‌ها بر اساس موقعیت متفاوت است)
5. از ابزارهای مدیریت هزینه Azure استفاده کنید

### پرسش: آیا گزینه‌های رایگان برای قالب‌های azd وجود دارد؟
**پاسخ**: برخی خدمات دارای SKUهای رایگان یا اعتبار ماهانه هستند که مشروط به واجد شرایط بودن، طرح میزبانی، منطقه، و محدودیت‌های اشتراک می‌باشند. این موارد باعث نمی‌شوند که کل قالب رایگان باشد: پایگاه‌های داده، جستجو، شبکه‌بندی، رجیستری، تله‌متری و استنتاج مدل می‌توانند هزینه‌های جداگانه‌ای داشته باشند. قبل از استقرار، فهرست [خدمات رایگان Azure](https://azure.microsoft.com/free/) و قیمت‌گذاری فعلی هر منبع را بررسی کنید.

### پرسش: چگونه هزینه‌ها را قبل از استقرار تخمین بزنم؟
**پاسخ**: 
1. فایل `main.bicep` قالب را بررسی کنید تا ببینید چه منابعی ایجاد می‌شوند
2. از ماشین حساب قیمت‌گذاری Azure با SKUهای مشخص استفاده کنید
3. ابتدا در یک محیط توسعه مستقر کنید تا هزینه‌های واقعی را مانیتور کنید
4. از Azure Cost Management برای تحلیل دقیق هزینه‌ها استفاده کنید

## بهترین شیوه‌ها

### پرسش: بهترین شیوه‌ها برای ساختار پروژه azd چیست؟
**پاسخ**: 
1. کد برنامه را جدا از زیرساخت نگه دارید
2. از نام‌های معنادار برای خدمات در `azure.yaml` استفاده کنید
3. مدیریت خطا مناسب را در اسکریپت‌های ساخت پیاده کنید
4. از پیکربندی خاص هر محیط استفاده کنید
5. مستندات جامع را شامل کنید

### پرسش: چگونه چندین سرویس را در azd سازماندهی کنم؟
**پاسخ**: از ساختار پیشنهادی زیر استفاده کنید:
```
├── src/
│   ├── web/          # Frontend service
│   ├── api/          # Backend service  
│   └── worker/       # Background service
├── infra/            # Infrastructure templates
├── azure.yaml        # azd configuration
└── README.md         # Project documentation
```

### پرسش: آیا باید پوشه `.azure` را به کنترل نسخه متعهد کنم؟
**پاسخ**: **خیر!** پوشه `.azure` حاوی اطلاعات حساس است. آن را به `.gitignore` اضافه کنید:
```gitignore
.azure/
```

### پرسش: چگونه با اسرار و پیکربندی حساس برخورد کنم؟
**پاسخ**: 
1. از Azure Key Vault برای مدیریت اسرار استفاده کنید
2. اسرار Key Vault را در پیکربندی برنامه ارجاع دهید
3. هرگز اسرار را به کنترل نسخه متعهد نکنید
4. از هویت‌های مدیریت شده برای احراز هویت سرویس به سرویس استفاده کنید

### پرسش: رویکرد پیشنهادی برای CI/CD با azd چیست؟
**پاسخ**: 
1. برای هر مرحله (توسعه/آزمایشی/تولید) محیط‌های جداگانه استفاده کنید
2. تست خودکار را قبل از استقرار پیاده‌سازی کنید
3. از سرویس پرینسیپال‌ها برای احراز هویت استفاده کنید
4. پیکربندی حساس را در اسرار/متغیرهای خط لوله ذخیره کنید
5. دروازه‌های تأیید برای استقرارهای تولید پیاده‌سازی کنید

## موضوعات پیشرفته

### پرسش: آیا می‌توانم azd را با عملکرد سفارشی گسترش دهم؟
**پاسخ**: بله، از طریق قلاب‌های استقرار در `azure.yaml`:
```yaml
hooks:
  predeploy:
    run: ./scripts/custom-setup.sh
  postdeploy:
    run: ./scripts/custom-config.sh
```

### پرسش: چگونه azd را با فرآیندهای موجود DevOps ادغام کنم؟
**پاسخ**: 
1. از دستورات azd در اسکریپت‌های خط لوله موجود استفاده کنید
2. قالب‌های azd را در تیم‌ها استاندارد کنید
3. با سیستم‌های مانیتورینگ و هشدار موجود ادغام کنید
4. از خروجی JSON azd برای ادغام در خط لوله استفاده کنید

### پرسش: آیا می‌توان azd را با Azure DevOps استفاده کرد؟
**پاسخ**: بله، azd با هر سیستم CI/CD کار می‌کند. خط لوله‌های Azure DevOps بسازید که از دستورات azd استفاده کنند.

### پرسش: چگونه در azd مشارکت کنم یا قالب‌های جامعه ایجاد کنم؟
**پاسخ**: 
1. **ابزار azd**: همکاری در [Azure/azure-dev](https://github.com/Azure/azure-dev)
2. **قالب‌ها**: پیروی از [دستورالعمل‌های مشارکت در گالری Awesome AZD](https://github.com/Azure/awesome-azd#3-contribute-to-gallery)
3. **مستندات**: همکاری در مستندات در [MicrosoftDocs/azure-dev-docs](https://github.com/MicrosoftDocs/azure-dev-docs)

### سؤال: نقشه راه azd چیست؟
**جواب**: برای ویژگی‌ها و بهبودهای برنامه‌ریزی شده به [نقشه راه رسمی](https://github.com/Azure/azure-dev/projects) مراجعه کنید.

### سؤال: چگونه از ابزارهای استقرار دیگر به azd مهاجرت کنم؟
**جواب**: 
1. تحلیل معماری فعلی استقرار
2. ایجاد قالب‌های معادل Bicep
3. پیکربندی `azure.yaml` برای تطبیق با خدمات فعلی
4. آزمایش کامل در محیط توسعه
5. مهاجرت تدریجی محیط‌ها
