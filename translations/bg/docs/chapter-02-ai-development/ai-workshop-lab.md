### **Лабораторно упражнение 3.1: Оптимизация на разходите**

**Задача**: Конфигурирайте шаблона за икономично развитие.

**Задачи:**
1. Изберете използваемата среда на работилницата: `azd env select myai-workshop`.
2. Запишете текущия Search SKU и капацитета на модела от `infra/main.parameters.json` и избраната среда.
3. Използвайте поддържаните входове по-долу след проверка на квотата за модел и регион:
   ```bash
   azd env set AZURE_SEARCH_SERVICE_SKU basic
   azd env set AZURE_OPENAI_CHATGPT_DEPLOYMENT_CAPACITY 10
   azd up
   ```
4. Потвърдете Search SKU и капацитета на разгръщането в портала и оценете разликата с калкулатора за ценообразуване. Не очаквайте веднага актуализация на данните за фактуриране.

**Критерии за успех:** Search използва Basic, чат разгръщането има поисканата поддържана мощност и приложението все още отговаря на примерен въпрос. Капацитетът `10` е разпределение на лимити за скорост, не е отстъпка за цена на токен. Смяната на Search tier може да е ограничена или изисква повторно създаване; не експериментирайте на производствени ресурси. F0 е специфично за услугата и не е SKU на Azure OpenAI модел.

## Модул 4: Сигурност и производствени добри практики

### Стъпка 4.1: Защитено управление на идентификационни данни

**Настоящ проблем**: Много AI приложения вграждат API ключове или използват несигурно съхранение.

**Решение чрез AZD**: Управлявана идентичност + интеграция с Key Vault.

1. **Прегледайте конфигурацията за сигурност в шаблона:**
```bash
# Look for Key Vault and Managed Identity configuration
grep -r "keyVault\|managedIdentity" infra/
```

2. **Потвърдете работата на управляваната идентичност:**
```bash
# For the sample's default Container Apps host
az containerapp identity show --name YOUR_CONTAINER_APP_NAME --resource-group YOUR_RG
```

### Стъпка 4.2: Мрежова сигурност

1. **Активирайте частни крайни точки** с използване на поддържаната мрежова конфигурация от примера (ако все още не са конфигурирани).

За вашия собствен шаблон, този илюстративен фрагмент показва връзката с OpenAI крайна точка. Необходим е също VNet, частна DNS конфигурация и свързаност на приложението; не го поставяйте без промяна в примера, който вече има модули за частни крайни точки:
```bicep
// Private endpoint for OpenAI
resource openAIPrivateEndpoint 'Microsoft.Network/privateEndpoints@2023-04-01' = {
  name: 'pe-openai-${uniqueString(resourceGroup().id)}'
  location: location
  properties: {
    subnet: {
      id: vnet.properties.subnets[0].id
    }
    privateLinkServiceConnections: [
      {
        name: 'openai-connection'
        properties: {
          privateLinkServiceId: openAIAccount.id
          groupIds: ['account']
        }
      }
    ]
  }
}
```

### Стъпка 5.2: Създаване на AZD шаблон

**Следвайте този модел, за да конвертирате приложението си:**

**Само решетка:** Тази секция не предоставя изходен код на API/уеб приложение, хост инфраструктура, разгръщания на модели, идентичност/RBAC или завършен `main.parameters.json`. Bicep за ресурсна група илюстрира композиция на модули; типично входно място с обхват на абонамент AZD трябва да създаде ресурсна група и да я извика на този обхват. Не очаквайте `azd up` да разгръща пълно приложение след копиране само на тези фрагменти. За работеща база продължете с RAG шаблона от Модул 1.

1. **Създайте основната структура:**
```bash
mkdir my-ai-app-azd
cd my-ai-app-azd

# Initialize AZD template
azd init --template minimal .
```

2. **Създайте azure.yaml:**
```yaml
# Metadata
name: my-ai-app
metadata:
  template: my-ai-app-template@0.0.1-beta

# Services definition
services:
  api:
    project: ./api
    host: containerapp
  web:
    project: ./web
    host: staticwebapp
    
# Hooks for custom deployment logic  
hooks:
  predeploy:
    shell: sh
    run: echo "Preparing AI models..."
```

3. **Създайте инфраструктурни шаблони:**

**infra/main.bicep** - Главен шаблон:
```bicep
@description('Primary location for all resources')
param location string = resourceGroup().location

@description('Name of the OpenAI service')
param openAIServiceName string = 'openai-${uniqueString(resourceGroup().id)}'

// Your AI services here
module openAI 'modules/openai.bicep' = {
  name: 'openai'
  params: {
    name: openAIServiceName
    location: location
  }
}
```

**infra/modules/openai.bicep** - OpenAI модул:
```bicep
@description('Name of the OpenAI service')
param name string

@description('Location for the OpenAI service')
param location string

resource openAIAccount 'Microsoft.CognitiveServices/accounts@2023-05-01' = {
  name: name
  location: location
  kind: 'OpenAI'
  sku: {
    name: 'S0'
  }
  properties: {
    customSubDomainName: name
    disableLocalAuth: true
  }
}

output endpoint string = openAIAccount.properties.endpoint
output name string = openAIAccount.name
```

## Модул 6: Отстраняване на често срещани проблеми

### Чести проблеми при разгръщане

#### Проблем 1: Превишена квота за OpenAI услуга
**Симптоми:** Разгръщането се проваля с грешка за квота
**Решения:**
```bash
# Check current quotas
az cognitiveservices usage list --location eastus

# Request quota increase, OR try a new disposable environment in another region.
# Azure resources cannot be relocated merely by changing AZURE_LOCATION.
azd env new myai-quota-test
azd env set AZURE_LOCATION westus2
azd up
```

#### Проблем 2: Моделът не е наличен в региона
**Симптоми:** AI отговорите се провалят или грешки при разгръщане на модел
**Решения:**
```bash
# Check model availability by region
az cognitiveservices model list --location eastus

# Update to available model
azd env set AZURE_OPENAI_CHATGPT_MODEL gpt-4.1-mini
azd up
```

#### Проблем 3: Проблеми с разрешенията
**Симптоми:** Грешки 403 Forbidden при повикване на AI услуги
**Решения:**
```bash
# Check role assignments
az role assignment list --scope /subscriptions/YOUR_SUB/resourceGroups/YOUR_RG

# Add missing roles
az role assignment create \
  --assignee YOUR_PRINCIPAL_ID \
  --role "Cognitive Services OpenAI User" \
  --scope /subscriptions/YOUR_SUB/resourceGroups/YOUR_RG
```

## Модул 7: Мониторинг и оптимизация

### Стъпка 7.1: Настройка на цялостен мониторинг

1. **Създайте персонализирани табла:**

Навигирайте до портала Azure и създайте табло с:
- Брой заявки към OpenAI и латентност
- Процент на грешки в приложението
- Използване на ресурси
- Проследяване на разходите

2. **Настройте сигнали:**
```bash
# Failed-request count on the Application Insights component (not a percentage)
az monitor metrics alert create \
  --name "AI-App-Failed-Requests" \
  --resource-group YOUR_RG \
  --scopes YOUR_APPLICATION_INSIGHTS_RESOURCE_ID \
  --condition "count requests/failed > 10" \
  --window-size 5m \
  --evaluation-frequency 1m \
  --description "More than 10 failed requests in five minutes"
```

Проверете дали компонентът излъчва телеметрия за заявки и добавете група действия, ако са необходими известия. Мярката е брой, а не процент на неуспех; сигнал за процент изисква подходяща заявка и знаменател.

### Стъпка 7.2: Оптимизация на разходите

1. **Анализирайте текущите разходи:**
```bash
# Set a recent reporting window supported by your billing account.

```

Заменете плейсхолдерите за дати. Поддръжката на Consumption API варира според споразумението за фактуриране; използвайте Cost Management в портала, ако детайлите за използването са недостъпни. Разходите са забавени, не са тест в реално време.

2. **Прилагайте контрол на разходите:**

- Мониторирайте използването на токени за OpenAI

## Финално предизвикателство: Пълна реализация

### Сценарий на предизвикателството

Това е **незадължително предизвикателство по архитектура/дизайн**, не предоставено изпълнимо упражнение или сертификация за продукция. Предложете чатбот за обслужване на клиенти с AI и документирайте кои изисквания изискват допълнително внедряване и доказателства:

**Функционални изисквания:**
- Уеб интерфейс за взаимодействия с клиенти
- Интеграция с Microsoft Foundry Models за отговори
- Търсене в документи с помощта на Azure AI Search
- Интеграция с съществуваща база данни на клиенти
- Многоезична поддръжка

**Нефункционални изисквания:**
- Обработка на 1000 едновременни потребители
- SLA с 99,9% наличност
- Съвместимост с SOC 2
- Разходи под 500$/месец
- Разгръщане в няколко среди (dev, staging, prod)

Това са хипотетични ограничения от заинтересованите страни, а не едновременно гарантирани резултати. Определете скорост на заявки, размери на подсказки/отговори и продължителност на сесията преди оценка на разходите; 1,000 едновременни потребители не установява работно натоварване или доказва, че бюджет от 500$ е възможен. SOC 2 е резултат от организационен одит, не превключвател, разрешен от AZD шаблон. Идентифицирайте компромиси и отхвърляйте невъзможни ограничения с доказателства.
