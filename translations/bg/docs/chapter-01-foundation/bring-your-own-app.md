## Въведение

В [Вашият първи проект](first-project.md) вие деплойнахте приложение, като започнахте от шаблон. Но повечето пъти вече *имате* приложение — Node.js API, Python Flask услуга, .NET уеб приложение — намиращо се в папка на вашата машина. Този урок показва как да добавите azd към съществуващия код, за да го деплойнете с `azd up`, без да е необходим шаблон.

## Цели за учене

В края на този урок ще:
- Разберете трите начина да стартирате azd проект
- Стартирате `azd init` в съществуваща кодова база
- Разберете какво правят `azure.yaml` и папката `infra/` за вашето приложение
- Знаете кога да оставите azd да генерира инфраструктура и кога да напишете собствена
- Деплойнете съществуващото приложение в Azure с `azd up`

## Резултати от учене

След завършване на този урок ще можете да:
- Инициализирате azd в проект, който вече имате
- Четете и редактирате основен файл `azure.yaml`
- Генерирате начална инфраструктура с `azd infra generate`
- Избирате подходящ Azure хост за вашето приложение
- Деплойвате и почиствате собственото си приложение

## Три начина за стартиране на azd проект

| Начална точка | Команда | Кога да използвате |
|----------------|---------|-------------|
| **От шаблон** | `azd init --template <name> .` (празна директория) | За учене или за започване на ново приложение от доказан пример |
| **От съществуващия ви код** | `azd init` (в папката на вашия проект) | Вече имате приложение и искате да го деплойнете |
| **От Git хранилище** | `azd init --from-code` (в клонирано хранилище) | Приемате azd за съществуващо хранилище |

Вече сте практикували първата опция. Този урок разглежда втората — най-често срещаният реален сценарий.

## Стъпка 1: Стартирайте `azd init` в Проекта си

Отворете терминал **вътре в папката на съществуващия ви проект** и изпълнете:

```bash
cd my-existing-app
azd init
```

azd ще попита как искате да инициализирате. Изберете:

```
? How do you want to initialize your app?
> Use code in the current directory
  Select a template
```

Изберете **"Използвай кода в текущата директория."** azd след това сканира папката ви, открива езика и рамката ви, и предлага хост.

### Какво открива azd

azd търси сигнали за приложението като `package.json`, `requirements.txt`, `pom.xml`, `*.csproj` или `Dockerfile`. Потокът от кода не е общ съветник за избор на хост за всяка поддържана цел на внедряване:

| Вашето приложение | Вероятно открит хост |
|----------|----------------------|
| Поддържано Node.js / Python / .NET уеб приложение | Обикновено Azure Container Apps; проверете генерираното определение |
| Контейнеризирано приложение (`Dockerfile`) | Azure Container Apps |
| Функция или проект за Static Web Apps | Използвайте съответстващ шаблон или създайте `azure.yaml` и инфраструктура, ако потокът от кода не поддържа вашия макет |

Потвърдете откритата услуга(и) и azd ще осигури необходимите ви файлове.

## Стъпка 2: Разберете какво е създадено от azd

След инициализация, разгледайте `azure.yaml`. Потокът на генерираната инфраструктура може да поддържа инфраструктурата неявна докато стартирате `azd infra generate`; не приемайте, че `infra/` вече съществува:

```
my-existing-app/
├── azure.yaml          # ← NEW: tells azd what to deploy and where
├── infra/              # Materialized with azd infra generate when using implicit infrastructure
│   ├── main.bicep
│   └── main.parameters.json
├── src/ (your code)    # unchanged
└── ...                 # your existing files, untouched
```

### `azure.yaml` — определението на проекта

Това е сърцето на azd проекта. Следващото **илюстративно определение на App Service** изисква съответстваща инфраструктура на App Service; това не е причина да променяте генерирания хост Container Apps без да променяте инфраструктурата:

```yaml
# azure.yaml
name: my-existing-app
services:
  web:
    project: ./src           # path to your app code
    language: js             # js | python | dotnet | java
    host: appservice         # appservice | containerapp | function | staticwebapp
```

Блокът `services` е ключовата част: всяка позиция съпоставя папка от кода ви с Azure хост. Ако вашето приложение има както frontend, така и API, ще имате две услуги.

### `infra/` — вашите Azure ресурси като код

Папката `infra/` съдържа Bicep файлове, които дефинират ресурсите в Azure, от които вашето приложение се нуждае (App Service, базата данни и др.). Не е нужно да ги пишете ръчно—azd генерира работна начална точка. Можете *да ги редактирате* по-късно, за да добавите ресурси или да затегнете сигурността (обсъжда се в [Глава 4](../chapter-04-infrastructure/README.md)).

> **Съвет:** Искате ли да видите или персонализирате генерираната инфраструктура преди разгръщането? Стартирайте `azd infra generate` (също налична като `azd infra synth`), за да запишете IaC на диска, така че да можете да я прегледате и да я управлявате с version control.

## Стъпка 3: Задайте необходимата конфигурация

Ако вашето приложение се нуждае от настройки или тайни (напр. низ за връзка, API ключ), не ги вграждайте директно в кода. Използвайте стойности от средата:

```bash
# Create an environment
azd env new dev

# Set a non-secret value
azd env set API_VERSION 1.0.0
```

Това съхранява стойността само локално. За да повлияете на приложението, изрично я използвайте в параметри на инфраструктурата, поддържана настройка на услуга или hook; задаването на произволна променлива не конфигурира разположеното изпълнение.

За реални тайни ги съхранявайте в Key Vault и ги препращайте от инфраструктурата си—вижте [Глава 3: Конфигурация и удостоверяване](../chapter-03-configuration/authsecurity.md).

## Стъпка 4: Разгръщане

Сега използвайте същия добре познат работен поток:

```bash
# Authenticate (required for azd)
azd auth login

# Preview the resources that will be created
azd provision --preview

# Provision infrastructure and deploy your code
azd up
```

Когато приключи, azd отпечатва URL на вашето приложение. Проверете го по същия начин както всяко azd приложение:

```bash
azd show           # show endpoints
azd monitor --logs # check logs if needed
```

## Чести проблеми при първоначално използване

| Симптом | Вероятна причина | Решение |
|---------|--------------|-----|
| azd не откри моето приложение | Липсва manifest (напр. `package.json`) | Добавете manifest, или изберете хоста ръчно по време на `azd init` |
| Сглобяването се проваля по време на `azd up` | Приложението се нуждае от стъпка за билдване | Конфигурирайте скриптовете за пакетиране на приложението или service `prepackage` hook; използвайте `dist` за изход от разгръщането, а не `buildCommand`/`outputPath` |
| Приложението стартира, но връща грешки | Липсва конфигурация/тайна | Свържете стойностите с настройки на приложението по време на изпълнение или препратка към Key Vault; само `azd env set` не е достатъчно |
| Избран е грешен хост | Автоматичното откриване не съответства на нуждите ви | Променете както `host:`, така и съответната инфраструктура, или изберете съвпадащ темплейт |

За повече информация вижте [Глава 7: Отстраняване на проблеми](../chapter-07-troubleshooting/README.md).

## Освобождаване на ресурси

```bash
azd down --force --purge
```

## Обобщение

- `azd init` → **"Използвай код в текущата директория"** добавя azd към вече съществуващо приложение.
- `azure.yaml` свързва папките с вашия код към Azure хостове; `infra/` дефинира ресурсите като Bicep.
- `azd infra generate` ви позволява да прегледате или персонализирате генерираната инфраструктура.
- След инициализация, съществуващото ви приложение използва същия `azd up` / `azd down` работен поток както приложение, базирано на темплейт.
