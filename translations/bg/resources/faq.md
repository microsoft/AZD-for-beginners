## Започване

### В: Какво е Azure Developer CLI (azd)?
**О**: Azure Developer CLI (azd) е команден инструмент, ориентиран към разработчиците, който ускорява времето за прехвърляне на вашето приложение от локалната среда за разработка към Azure. Той предлага най-добрите практики чрез шаблони и подпомага целия жизнен цикъл на деплоймента.

### В: Как azd се различава от Azure CLI?
**О**: 
- **Azure CLI**: Универсален инструмент за управление на ресурси в Azure
- **azd**: Инструмент, фокусиран върху разработчиците за работни потоци при деплоймент на приложения
- azd има собствена система за удостоверяване и процес на деплоймент; Azure CLI е отделен, допълващ инструмент
- azd включва шаблони, управление на среди и автоматизация на деплоймента

### В: Нужно ли е да имам инсталиран Azure CLI, за да използвам azd?
**О**: Не за основния AZD работен поток. Автентикирайте се с `azd auth login`. Инсталирайте Azure CLI отделно, когато шаблонният hook или упражнение явно изпълняват `az` команди.

### В: Кои програмни езици поддържа azd?
**О**: azd е езиково независим. Работи с:
- Node.js/JavaScript/TypeScript
- Python
- .NET/C#
- Java
- Go
- PHP
- Статични уебсайтове
- Контейнеризирани приложения

### В: Мога ли да използвам azd с вече съществуващи проекти?
**О**: Да! Можете:
1. Да използвате `azd init` за добавяне на конфигурация на azd към съществуващи проекти
2. Да адаптирате съществуващите проекти, за да съвпаднат със структурата на azd шаблони
3. Да създадете персонализирани шаблони базирани на вашата съществуваща архитектура

### В: Какво се промени с общата наличност на разширението Foundry?
**О**: Пакетът `microsoft.foundry` достигна версия 1.0 и GA на 5 ноември 2026 г. С AZD 1.37.0+ използвайте `azd ext install microsoft.foundry` за инсталиране на седем основни разширения за агенти, връзки, инспектор, проекти, рутини, умения и инструментални кутии. Това не е ново командно пространство, а компонентите му са с независими версии. Оценки, набори от данни, фино настройване и персонализирани модели се инсталират отделно; опционалните функции в предварителен преглед не стават GA само защото пакетът е GA.

Ръководството [hosted-agent walkthrough](../docs/chapter-02-ai-development/microsoft-foundry-integration.md#hosted-agent-walkthrough-ga) използва Python 3.13+ и актуалната версия на uv. `azd ai agent run` отваря Agent Inspector локално, но повикванията към модела все още използват Azure и генерират такси. Режимът на код `azd deploy` качва сорс кода за отдалечена компилация без необходимост от локална компилация в контейнер.

### Въпрос: Премахва ли `azd down` hosted агент от съществуващ проект Foundry?
**Отговор**: Не за пътя с повторна употреба на проект, описан в хостван агент quickstart-а: той оставя проекта, hosted агент и други ресурси на място. Премахнете нежеланите ресурси отделно без да изтривате споделени ресурси. Ако средата е създала нов проект Foundry, `azd down` изтрива неговата ресурсна група и всичко в нея. Прегледайте [инструкциите за почистване](../docs/chapter-02-ai-development/microsoft-foundry-integration.md#7-clean-up-deliberately) и подкана за изтриване преди да потвърдите.

## Автентикация и достъп

### Въпрос: Как се автентикирам в Azure с azd?
**Отговор**: Използвайте `azd auth login`, който ще отвори браузър за автентикация в Azure. За CI/CD сценарии използвайте service principals или управлявани идентичности.

### Въпрос: Мога ли да използвам azd с няколко Azure абонамента?
**Отговор**: Да. Използвайте `azd env set AZURE_SUBSCRIPTION_ID <subscription-id>`, за да определите кой абонамент да се използва за всяка среда.

### Въпрос: Какви разрешения са ми нужни за деплой с azd?
**Отговор**: Обикновено ви трябват:
- Ролята **Contributor** в ресурсната група или абонамента
- **User Access Administrator**, ако деплойвате ресурси, които изискват ролеви назначения
- Специфични разрешения варират според шаблона и ресурсите, които се деплойват

### Въпрос: Мога ли да използвам azd в CI/CD тръбопроводи?
**Отговор**: Абсолютно! azd е проектиран за интеграция със CI/CD. Използвайте service principals за автентикация и задайте променливи на средата за конфигурация.

### Въпрос: Как да обработвам автентикация в GitHub Actions?
**Отговор**: Предпочитайте федерация на идентичността на натоварването (OIDC), конфигурирана с `azd pipeline config`. Генерираният workflow инсталира AZD и автентикира AZD директно с федеративна идентичност. Самостоятелен `azure/login` стъпка не установява AZD логин. Стъпката за логин в съществуваща задача е:
```yaml
permissions:
  contents: read
  id-token: write
steps:
  - uses: actions/checkout@v7
  - uses: Azure/setup-azd@v2
  - run: >-
      azd auth login
      --client-id "${{ vars.AZURE_CLIENT_ID }}"
      --tenant-id "${{ vars.AZURE_TENANT_ID }}"
      --federated-credential-provider github
```

Произведете или деплойвайте след логин, с конфигурирана желаната AZD среда, абонамент и местоположение. Федеративният идентификатор трябва да има доверие към репозитория/референт на workflow-а или GitHub средата и ролите му в Azure трябва да позволяват исканите операции.

## Шаблони и проекти

### Въпрос: Къде мога да намеря azd шаблони?
**Отговор**: 
- Официални и общностни шаблони: [Awesome AZD](https://azure.github.io/awesome-azd/)
- Общностни шаблони: търсене в GitHub за "azd-template"
- Използвайте `azd template list`, за да разглеждате налични шаблони

### Въпрос: Как създавам персонализиран шаблон?
**Отговор**: 
1. Започнете с вече съществуваща структура на шаблон
2. Променете `azure.yaml`, инфраструктурните файлове и кода на приложението
3. Тествате основно с `azd up`
4. Публикувайте в GitHub с подходящи тагове

### Въпрос: Мога ли да използвам azd без шаблон?
**Отговор**: Да, използвайте `azd init` в съществуващ проект, за да създадете необходимите конфигурационни файлове. Ще трябва ръчно да конфигурирате `azure.yaml` и инфраструктурните файлове.

### Въпрос: Каква е разликата между официални и общностни шаблони?
**Отговор**: 
- **Официални шаблони**: Поддържани от Microsoft, редовно актуализирани, с обширна документация
- **Общностни шаблони**: Създадени от разработчици, могат да имат специализирани случаи на употреба, качество и поддръжка варират

### Въпрос: Как обновя шаблон в моя проект?
**Отговор**: Шаблоните не се обновяват автоматично. Можете:
1. Ръчно да сравните и сливате промени от източниковия шаблон
2. Стартирайте наново с `azd init`, използвайки актуализирания шаблон
3. Изберете конкретни подобрения от обновените шаблони

## Деплой и инфраструктура

### Въпрос: Какви Azure услуги може да деплойне azd?
**Отговор**: azd може да деплойне всяка Azure услуга чрез Bicep/ARM шаблони, включително:
- App Services, Container Apps, Functions
- Бази данни (SQL, PostgreSQL, Cosmos DB)
- Storage, Key Vault, Application Insights
- Мрежови, сигурност и мониторинг ресурси

### Въпрос: Мога ли да деплойна в няколко региона?
**Отговор**: Да, конфигурирайте множество региони във вашите Bicep шаблони и задайте параметъра за местоположение съответно за всяка среда.

### Въпрос: Как да обработвам миграции на база данни?
**Отговор**: Използвайте hooks за деплой в `azure.yaml`:
```yaml
hooks:
  postdeploy:
    posix:
      run: ./scripts/migrate-database.sh
    windows:
      run: ./scripts/migrate-database.ps1
```

### Въпрос: Мога ли да деплойна само инфраструктурата без приложения?
**Отговор**: Да, използвайте `azd provision`, за да деплойнете само инфраструктурните компоненти, дефинирани във вашите шаблони.

### Въпрос: Как да деплойна към съществуващи Azure ресурси?
**Отговор**: Да, когато шаблонът го поддържа. Позовете се на съществуващи ресурси чрез Bicep декларации `existing` или параметрите за съществуващи ресурси, описани в шаблона, и насочвайте услужните услуги към намерените цели. Това не импортира собственост или автоматично създава липсващи разрешения. Прегледайте шаблона преди деплой.

### Въпрос: Мога ли да използвам Terraform вместо Bicep?
**Отговор**: Да. AZD поддържа както Terraform, така и Bicep. Изберете шаблон базиран на Terraform или конфигурирайте `infra.provider: terraform` в `azure.yaml` с подходящите Terraform файлове и състояние/backend конфигурация. Вижте [Terraform workflow](https://learn.microsoft.com/azure/developer/azure-developer-cli/use-terraform-for-azd).

## Конфигурация и среди

### Въпрос: Как управлявам различни среди (dev, staging, prod)?
**Отговор**: Създайте отделни среди с `azd env new <environment-name>` и конфигурирайте различни настройки за всяка:
```bash
azd env new development
azd env new staging  
azd env new production
```

### Въпрос: Къде се съхраняват конфигурациите на средата?
**Отговор**: В папката `.azure` във вашата проектна директория. Всяка среда има своя папка с конфигурационни файлове.

### Въпрос: Как задавам конфигурация специфична за среда?
**Отговор**: Използвайте `azd env set`, за да конфигурирате променливи на средата:
```bash
azd env set AZURE_LOCATION eastus
azd env set DATABASE_TIER Basic
```

### Въпрос: Мога ли да споделям конфигурации на средата с други членове на екипа?
**Отговор**: Папката `.azure` съдържа чувствителна информация и не трябва да се комитва във version control. Вместо това:
1. Документирайте необходимите променливи на средата
2. Използвайте скриптове за деплой, за да настройвате среди
3. Използвайте Azure Key Vault за чувствителни конфигурации

### Въпрос: Как презаписвам шаблонните по подразбиране стойности?
**Отговор**: Задайте променливи на средата, съответстващи на параметрите на шаблона:
```bash
azd env set AZURE_LOCATION westus2
azd env set SKU_NAME "B1"
```

Само променливите, използвани от шаблона, влияят на деплоймента. `SKU_NAME` по-горе е пример за персонализиран вход, а не универсална AZD настройка.

## Отстраняване на проблеми

### Въпрос: Защо `azd up` не успява?
**Отговор**: Чести причини:
1. **Проблеми с автентикацията**: Изпълнете `azd auth login`
2. **Недостатъчни разрешения**: Проверете вашите Azure ролеви назначения
3. **Конфликти при именуване на ресурси**: Прегледайте конфликтиращия ресурс и входовете за имена в шаблона; създайте отделна среда с `azd env new`, когато е нужен изолиране
4. **Проблеми с квоти/капацитет**: Проверете регионалната наличност
5. **Грешки в шаблона**: Валидирайте Bicep шаблони

### Въпрос: Как отстранявам грешки при провалени деплойменти?
**Отговор**: 
1. Използвайте `azd deploy --debug` за подробен изход
2. Проверете историята на деплойментите в Azure портала
3. Прегледайте Activity Log в Azure портала
4. Използвайте `azd show`, за да покажете текущото състояние на средата

### Въпрос: Защо променливите на моята среда не работят?
**Отговор**: Проверете:
1. Имената на променливите съвпадат точно с параметрите на шаблона
2. Стойностите са коректно цитирани, ако съдържат интервали
3. Избрана е средата: `azd env select <environment>`
4. Променливите са зададени в правилната среда

### Въпрос: Как изчиствам неуспешни деплойменти?
**Отговор**: 
```bash
azd down
```
Първо прегледайте избраната среда и потвърждението за изтриване. Това изтрива разположените Azure ресурси, а не локалната конфигурация на средата `.azure`. `--purge` също така изисква постоянно изтриване на поддържани ресурси, изтрити "меко", и може да бъде блокирано от защита при задържане/прочистване; това не е рутинна стъпка за възстановяване.

### Въпрос: Защо моето приложение не е достъпно след деплой?
**Отговор**: Проверете:
1. Деплойментът е приключил успешно
2. Приложението работи (проверете логовете в Azure портала)
3. Мрежовите групи за сигурност позволяват трафик
4. DNS/потребителските домейни са правилно конфигурирани

## Разходи и таксуване

### Въпрос: Колко ще струват деплойментите с azd?
**Отговор**: Разходите зависят от:
- Деплойнтите Azure услуги
- Избраните нива на услугите/SKU-та
- Регионални ценови разлики
- Модели на използване

Използвайте [Azure Pricing Calculator](https://azure.microsoft.com/pricing/calculator/) за оценки.

### Въпрос: Как да контролирам разходите при деплоймент с azd?
**Отговор**: 
1. Използвайте по-ниски нива SKU за развойни среди
2. Настройте Azure бюджети и аларми
3. Използвайте `azd down` за премахване на ресурси, когато не са нужни
4. Избирайте подходящи региони (цените варират по местоположение)
5. Използвайте Azure Cost Management инструменти

### В: Има ли безплатни опции в azd шаблоните?
**О**: Някои услуги имат безплатни SKU или месечни кредити, в зависимост от допустимост, план за хостинг, регион и ограничения на абонамента. Това не прави цял шаблон безплатен: базите данни, търсенето, мрежите, регистрите, телеметрията и моделирането могат да възникнат със самостоятелни такси. Проверете [списъка с безплатни услуги в Azure](https://azure.microsoft.com/free/) и актуалните цени за всеки ресурс преди внедряване.

### В: Как да оценя разходите преди внедряване?
**О**: 
1. Прегледайте `main.bicep` на шаблона, за да видите какви ресурси се създават
2. Използвайте Azure Pricing Calculator с конкретни SKU
3. Първо внедрете в развойна среда, за да наблюдавате реалните разходи
4. Използвайте Azure Cost Management за подробен анализ на разходите

## Най-добри практики

### В: Какви са най-добрите практики за структурата на azd проекта?
**О**: 
1. Дръжте кода на приложението отделен от инфраструктурата
2. Използвайте смислени имена на услуги в `azure.yaml`
3. Прилагайте правилна обработка на грешки в build скриптовете
4. Използвайте конфигурация, специфична за околната среда
5. Включвайте изчерпателна документация

### В: Как да организирам множество услуги в azd?
**О**: Използвайте препоръчаната структура:
```
├── src/
│   ├── web/          # Frontend service
│   ├── api/          # Backend service  
│   └── worker/       # Background service
├── infra/            # Infrastructure templates
├── azure.yaml        # azd configuration
└── README.md         # Project documentation
```

### В: Трябва ли да комитвам папката `.azure` във version control?
**О**: **Не!** Папката `.azure` съдържа чувствителна информация. Добавете я в `.gitignore`:
```gitignore
.azure/
```

### В: Как да управлявам тайни и чувствителна конфигурация?
**О**: 
1. Използвайте Azure Key Vault за тайни
2. Реферирайте тайни от Key Vault в конфигурацията на приложението
3. Никога не комитвайте тайни във version control
4. Използвайте управлявани идентичности за автентикация между услуги

### В: Какъв е препоръчаният подход за CI/CD с azd?
**О**: 
1. Използвайте отделни среди за всеки етап (разработка/тестване/производство)
2. Прилагайте автоматизирано тестване преди внедряване
3. Използвайте service principals за автентикация
4. Съхранявайте чувствителна конфигурация в тайни/променливи на pipeline
5. Прилагайте одобрителни контроли за производствени внедрявания

## Напреднали теми

### В: Мога ли да разширя azd с персонализирана функционалност?
**О**: Да, чрез deployment hooks в `azure.yaml`:
```yaml
hooks:
  predeploy:
    run: ./scripts/custom-setup.sh
  postdeploy:
    run: ./scripts/custom-config.sh
```

### В: Как да интегрирам azd с вече съществуващи DevOps процеси?
**О**: 
1. Използвайте azd команди в съществуващи скриптове на pipeline
2. Стандартизирайте използването на azd шаблони в екипите
3. Интегрирайте с вече съществуващ мониторинг и алармиране
4. Използвайте JSON изхода на azd за интеграция в pipeline

### В: Мога ли да използвам azd с Azure DevOps?
**О**: Да, azd работи с всяка CI/CD система. Създайте Azure DevOps pipelines, които използват azd команди.
