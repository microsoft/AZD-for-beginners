## Начало работы

### В: Что такое Azure Developer CLI (azd)?
**О**: Azure Developer CLI (azd) — это ориентированный на разработчика инструмент командной строки, который ускоряет время доставки вашего приложения из локальной среды разработки в Azure. Он предоставляет лучшие практики через шаблоны и помогает управлять полным циклом развертывания.

### В: Чем azd отличается от Azure CLI?
**О**: 
- **Azure CLI**: Универсальный инструмент для управления ресурсами Azure
- **azd**: Инструмент, ориентированный на разработчиков, для рабочих процессов развертывания приложений
- azd имеет собственную аутентификацию и процесс развертывания; Azure CLI — отдельный, дополнительный инструмент
- azd включает шаблоны, управление окружениями и автоматизацию развертывания

### В: Нужно ли устанавливать Azure CLI для использования azd?
**О**: Нет, для основного рабочего процесса AZD это не требуется. Аутентификация происходит с помощью `azd auth login`. Устанавливайте Azure CLI отдельно, если шаблон или упражнение явно запускают команды `az`.

### В: Какие языки программирования поддерживает azd?
**О**: azd не зависит от языка. Он работает с:
- Node.js/JavaScript/TypeScript
- Python
- .NET/C#
- Java
- Go
- PHP
- Статическими веб-сайтами
- Приложениями в контейнерах

### В: Могу ли я использовать azd с существующими проектами?
**О**: Да! Вы можете либо:
1. Использовать `azd init` для добавления конфигурации azd в существующие проекты
2. Адаптировать существующие проекты к структуре шаблонов azd
3. Создавать пользовательские шаблоны на основе вашей существующей архитектуры

### В: Что изменилось с выпуском расширения Foundry?
**О**: Пакет `microsoft.foundry` достиг версии 1.0 и вышел в GA 5 ноября 2026 года. С AZD версии 1.37.0 и выше используйте `azd ext install microsoft.foundry` для установки семи основных расширений для агентов, подключений, инспектора, проектов, рутин, навыков и наборов инструментов. Это не новое пространство имён команд, а компоненты независимо версионированы. Оценки, наборы данных, дообучение и пользовательские модели устанавливаются отдельно; предварительные функции не становятся GA только из-за GA пакета.

Пошаговое руководство [hosted-agent walkthrough](../docs/chapter-02-ai-development/microsoft-foundry-integration.md#hosted-agent-walkthrough-ga) использует Python 3.13+ и текущий uv. `azd ai agent run` открывает локально Agent Inspector, но вызовы моделей всё ещё используют Azure и тарифицируются. Режим кода `azd deploy` загружает исходники для удалённой сборки без необходимости локальной сборки контейнера.

### В: Удаляет ли `azd down` размещённого агента из существующего проекта Foundry?
**О**: Нет, для пути переиспользования проекта, описанного в быстром старте hosted-agent: агент, проект и другие ресурсы остаются на месте. Удаляйте ненужные ресурсы отдельно, не удаляя общие ресурсы. Если среда создала новый проект Foundry, `azd down` удаляет группу ресурсов и всё в ней. Ознакомьтесь с [руководством по очистке](../docs/chapter-02-ai-development/microsoft-foundry-integration.md#7-clean-up-deliberately) и запросами на удаление перед подтверждением.

## Аутентификация и доступ

### В: Как выполнить аутентификацию в Azure с помощью azd?
**О**: Используйте `azd auth login`, который откроет окно браузера для аутентификации в Azure. Для CI/CD сценариев используйте служебные учётные записи или управляемые идентичности.

### В: Можно ли использовать azd с несколькими подписками Azure?
**О**: Да. Используйте `azd env set AZURE_SUBSCRIPTION_ID <subscription-id>` для указания, какую подписку использовать для каждого окружения.

### В: Какие разрешения нужны для развертывания с azd?
**О**: Обычно вам нужны:
- Роль **Contributor** для группы ресурсов или подписки
- Роль **User Access Administrator**, если развертываете ресурсы, требующие назначений ролей
- Конкретные разрешения зависят от шаблона и развертываемых ресурсов

### В: Можно ли использовать azd в CI/CD пайплайнах?
**О**: Абсолютно! azd разработан для интеграции в CI/CD. Используйте служебные учётные записи для аутентификации и задавайте переменные окружения для настройки.

### В: Как обрабатывать аутентификацию в GitHub Actions?
**О**: Предпочитайте федерацию идентичностей рабочего процесса (OIDC), настраиваемую с помощью `azd pipeline config`. Сгенерированный workflow устанавливает AZD и аутентифицирует его напрямую через федеративную идентичность. Шаг `azure/login` сам по себе не устанавливает вход в AZD. Шаг входа в рамках существующей задачи выглядит так:
```yaml
permissions:
  contents: read
  id-token: write
steps:
  - uses: actions/checkout@v7
  - uses: Azure/setup-azd@v2
  - run: >-
      azd auth login
      --client-id "${{ vars.AZURE_CLIENT_ID }}"
      --tenant-id "${{ vars.AZURE_TENANT_ID }}"
      --federated-credential-provider github
```

Выполните подготовку или развертывание после входа, с настроенными нужными окружением AZD, подпиской и регионом. Федеративные учетные данные должны доверять репозиторию/ref workflow или окружению GitHub, а роли Azure должны разрешать запрашиваемые операции.

## Шаблоны и проекты

### В: Где найти шаблоны azd?
**О**: 
- Официальные и пользовательские шаблоны: [Awesome AZD](https://azure.github.io/awesome-azd/)
- Пользовательские шаблоны: поиск по GitHub по "azd-template"
- Используйте `azd template list` для просмотра доступных шаблонов

### В: Как создать пользовательский шаблон?
**О**: 
1. Начните с существующей структуры шаблона
2. Измените `azure.yaml`, файлы инфраструктуры и код приложения
3. Тщательно тестируйте с помощью `azd up`
4. Опубликуйте на GitHub с соответствующими тегами

### В: Можно ли использовать azd без шаблона?
**О**: Да, используйте `azd init` в существующем проекте для создания необходимых конфигурационных файлов. Вам нужно будет вручную настроить `azure.yaml` и файлы инфраструктуры.

### В: В чём разница между официальными и пользовательскими шаблонами?
**О**: 
- **Официальные шаблоны**: Поддерживаются Microsoft, регулярно обновляются, полная документация
- **Пользовательские шаблоны**: Созданы разработчиками, могут иметь специализированные случаи использования, разное качество и поддержку

### В: Как обновить шаблон в моём проекте?
**О**: Шаблоны не обновляются автоматически. Вы можете:
1. Вручную сравнить и объединить изменения с исходным шаблоном
2. Начать заново с помощью `azd init` с обновлённым шаблоном
3. Выбирать отдельные улучшения из обновлённых шаблонов

## Развертывание и инфраструктура

### В: Какие сервисы Azure может развернуть azd?
**О**: azd может развернуть любые сервисы Azure через Bicep/ARM шаблоны, включая:
- App Services, Container Apps, Functions
- Базы данных (SQL, PostgreSQL, Cosmos DB)
- Хранилища, Key Vault, Application Insights
- Ресурсы сети, безопасности и мониторинга

### В: Можно ли развертывать в нескольких регионах?
**О**: Да, настройте несколько регионов в шаблонах Bicep и задайте параметр location соответственно для каждого окружения.

### В: Как управлять миграциями схем баз данных?
**О**: Используйте хуки развертывания в `azure.yaml`:
```yaml
hooks:
  postdeploy:
    posix:
      run: ./scripts/migrate-database.sh
    windows:
      run: ./scripts/migrate-database.ps1
```

### В: Можно ли развернуть только инфраструктуру без приложений?
**О**: Да, используйте `azd provision` для развертывания только компонентов инфраструктуры, определённых в ваших шаблонах.

### В: Как развернуть на существующие ресурсы Azure?
**О**: Да, если шаблон это поддерживает. Используйте ссылки на существующие ресурсы с помощью деклараций `existing` в Bicep или параметров для существующих ресурсов, задокументированных в шаблоне, и сопоставьте сервисы приложения с целевыми ресурсами. Это не импортирует права собственности и не создаёт автоматически недостающие разрешения. Ознакомьтесь с шаблоном перед развертыванием.

### В: Можно ли использовать Terraform вместо Bicep?
**О**: Да. AZD поддерживает Terraform наряду с Bicep. Выберите шаблон на основе Terraform или настройте `infra.provider: terraform` в `azure.yaml`, включая соответствующие Terraform файлы и конфигурацию состояния/бэкенда. Смотрите [Рабочий процесс Terraform](https://learn.microsoft.com/azure/developer/azure-developer-cli/use-terraform-for-azd).

## Конфигурация и окружения

### В: Как управлять разными окружениями (dev, staging, prod)?
**О**: Создайте отдельные окружения с помощью `azd env new <environment-name>` и настройте разные параметры для каждого:
```bash
azd env new development
azd env new staging  
azd env new production
```

### В: Где хранятся конфигурации окружений?
**О**: В папке `.azure` в каталоге вашего проекта. Каждое окружение имеет свою папку с конфигурационными файлами.

### В: Как задать конфигурацию, специфичную для окружения?
**О**: Используйте `azd env set` для настройки переменных окружения:
```bash
azd env set AZURE_LOCATION eastus
azd env set DATABASE_TIER Basic
```

### В: Можно ли делиться конфигурациями окружения между членами команды?
**О**: Папка `.azure` содержит конфиденциальную информацию и не должна добавляться в систему контроля версий. Вместо этого:
1. Документируйте необходимые переменные окружения
2. Используйте скрипты развертывания для настройки окружений
3. Используйте Azure Key Vault для чувствительной конфигурации

### В: Как переопределить значения по умолчанию шаблона?
**О**: Задайте переменные окружения, соответствующие параметрам шаблона:
```bash
azd env set AZURE_LOCATION westus2
azd env set SKU_NAME "B1"
```

Только переменные, используемые шаблоном, влияют на развертывание. `SKU_NAME` выше — пример пользовательского входа, а не универсальная настройка AZD.

## Устранение неполадок

### В: Почему `azd up` не работает?
**О**: Распространённые причины:
1. **Проблемы с аутентификацией**: Запустите `azd auth login`
2. **Недостаточные разрешения**: Проверьте назначения ролей в Azure
3. **Конфликты имён ресурсов**: Проверьте конфликтующий ресурс и входы имен в шаблоне; создайте отдельное окружение с `azd env new` при необходимости изоляции
4. **Проблемы с квотами/мощностями**: Проверьте доступность в регионе
5. **Ошибки шаблона**: Проверьте шаблоны Bicep

### В: Как отлаживать ошибки развертывания?
**О**: 
1. Используйте `azd deploy --debug` для подробного вывода
2. Проверьте историю развертываний в портале Azure
3. Просмотрите Журнал активности в портале Azure
4. Используйте `azd show` для отображения состояния текущего окружения

### В: Почему мои переменные окружения не работают?
**О**: Проверьте:
1. Имена переменных точно совпадают с параметрами шаблона
2. Значения корректно заключены в кавычки, если содержат пробелы
3. Выбрано нужное окружение: `azd env select <environment>`
4. Переменные заданы в правильном окружении

### В: Как очистить неудачные развертывания?
**О**: 
```bash
azd down
```
 Сначала проверьте выбранное окружение и подтверждение удаления. Это удалит подготовленные ресурсы Azure, но не локальную конфигурацию окружения `.azure`. `--purge` дополнительно запрашивает окончательное удаление поддерживаемых ресурсов с мягким удалением и может блокироваться защитой удержания/очистки; это не рутинный шаг восстановления.

### В: Почему моё приложение недоступно после развертывания?
**О**: Проверьте:
1. Развертывание прошло успешно
2. Приложение запущено (проверьте логи в портале Azure)
3. Группы сетевой безопасности разрешают трафик
4. DNS/пользовательские домены настроены правильно

## Стоимость и биллинг

### В: Сколько будут стоить развертывания azd?
**О**: Стоимость зависит от:
- Развернутых сервисов Azure
- Выбранных уровней обслуживания/SKU
- Региональных различий в ценах
- Паттернов использования

Используйте [Калькулятор цен Azure](https://azure.microsoft.com/pricing/calculator/) для оценки.

### В: Как контролировать затраты при развертываниях azd?
**О**: 
1. Используйте нижестоящие SKU для сред разработки
2. Настройте бюджеты и оповещения в Azure
3. Используйте `azd down` для удаления ресурсов, когда они не нужны
4. Выбирайте подходящие регионы (стоимость варьируется в зависимости от расположения)
5. Используйте инструменты управления затратами Azure

### В: Есть ли бесплатные варианты тарифов для шаблонов azd?
**О**: Некоторые сервисы имеют бесплатные тарифы или ежемесячные гранты, при условии соответствия требованиям, плана хостинга, региона и ограничений подписки. Это не означает, что весь шаблон бесплатен: базы данных, поиск, сеть, реестр, телеметрия и вывод модели могут начислять отдельные платежи. Проверьте [список бесплатных сервисов Azure](https://azure.microsoft.com/free/) и актуальные цены для каждого ресурса перед развертыванием.

### В: Как оценить стоимость до развертывания?
**О**: 
1. Ознакомьтесь с `main.bicep` шаблона, чтобы увидеть, какие ресурсы создаются
2. Используйте калькулятор цен Azure с конкретными SKU
3. Сначала разверните в среде разработки для мониторинга реальных затрат
4. Используйте Azure Cost Management для подробного анализа стоимости

## Лучшие практики

### В: Какие лучшие практики по структуре проекта azd?
**О**: 
1. Разделяйте код приложения и инфраструктуру
2. Используйте значимые имена сервисов в `azure.yaml`
3. Реализуйте корректную обработку ошибок в скриптах сборки
4. Используйте конфигурацию, специфичную для среды
5. Включайте подробную документацию

### В: Как организовать несколько сервисов в azd?
**О**: Используйте рекомендуемую структуру:
```
├── src/
│   ├── web/          # Frontend service
│   ├── api/          # Backend service  
│   └── worker/       # Background service
├── infra/            # Infrastructure templates
├── azure.yaml        # azd configuration
└── README.md         # Project documentation
```

### В: Следует ли сохранять папку `.azure` в систему контроля версий?
**О**: **Нет!** Папка `.azure` содержит конфиденциальную информацию. Добавьте её в `.gitignore`:
```gitignore
.azure/
```

### В: Как обращаться с секретами и конфиденциальной конфигурацией?
**О**: 
1. Используйте Azure Key Vault для секретов
2. Ссылайтесь на секреты Key Vault в конфигурации приложения
3. Никогда не коммитьте секреты в систему контроля версий
4. Используйте управляемые идентичности для аутентификации между сервисами

### В: Каков рекомендуемый подход к CI/CD с azd?
**О**: 
1. Используйте отдельные среды для каждой стадии (разработка/предварительное тестирование/прод)
2. Реализуйте автоматическое тестирование перед развертыванием
3. Используйте сервисные принципы для аутентификации
4. Храните конфиденциальную конфигурацию в секретах/переменных пайплайна
5. Внедрите утверждающие ворота для развертываний в продакшн

## Продвинутые темы

### В: Можно ли расширить azd пользовательским функционалом?
**О**: Да, через хуки развертывания в `azure.yaml`:
```yaml
hooks:
  predeploy:
    run: ./scripts/custom-setup.sh
  postdeploy:
    run: ./scripts/custom-config.sh
```

### В: Как интегрировать azd с существующими процессами DevOps?
**О**: 
1. Используйте команды azd в существующих скриптах пайплайна
2. Стандартизируйте шаблоны azd в командах
3. Интегрируйтесь с существующими системами мониторинга и оповещений
4. Используйте JSON-вывод azd для интеграции с пайплайнами

### В: Можно ли использовать azd с Azure DevOps?
**О**: Да, azd работает с любой CI/CD системой. Создавайте пайплайны Azure DevOps, использующие команды azd.

### В: Как внести вклад в azd или создавать шаблоны сообщества?
**О**: 
1. **Инструмент azd**: внесите вклад в [Azure/azure-dev](https://github.com/Azure/azure-dev)
2. **Шаблоны**: следуйте [инструкциям по внесению в галерею Awesome AZD](https://github.com/Azure/awesome-azd#3-contribute-to-gallery)
3. **Документация**: помогайте в документации [MicrosoftDocs/azure-dev-docs](https://github.com/MicrosoftDocs/azure-dev-docs)

### В: Каков план развития azd?
**О**: Ознакомьтесь с [официальным роадмапом](https://github.com/Azure/azure-dev/projects) для планируемых функций и улучшений.

### В: Как перейти с других инструментов развертывания на azd?
**О**: 
1. Проанализируйте текущую архитектуру развертывания
2. Создайте эквивалентные шаблоны Bicep
3. Настройте `azure.yaml` для соответствия текущим сервисам
4. Тщательно протестируйте в среде разработки
5. Постепенно переносите среды
