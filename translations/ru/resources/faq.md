## Начало работы

### В: Что такое Azure Developer CLI (azd)?
**О**: Azure Developer CLI (azd) — это командный инструмент, ориентированный на разработчика, который ускоряет переход вашего приложения из локальной среды разработки в Azure. Он предоставляет лучшие практики через шаблоны и помогает с полным циклом развертывания.

### В: Чем azd отличается от Azure CLI?
**О**: 
- **Azure CLI**: Универсальный инструмент для управления ресурсами Azure
- **azd**: Инструмент, ориентированный на разработчиков, для рабочих процессов развертывания приложений
- azd имеет собственную аутентификацию и рабочий процесс развертывания; Azure CLI является отдельным, дополнительным инструментом
- azd включает шаблоны, управление средами и автоматизацию развертывания

### В: Нужно ли устанавливать Azure CLI для работы с azd?
**О**: Нет, для основного рабочего процесса AZD. Аутентифицируйтесь с помощью `azd auth login`. Устанавливайте Azure CLI отдельно, когда в шаблоне или упражнении явно запускаются команды `az`.

### В: Какие языки программирования поддерживает azd?
**О**: azd является языконезависимым. Он работает с:
- Node.js/JavaScript/TypeScript
- Python
- .NET/C#
- Java
- Go
- PHP
- Статическими веб-сайтами
- Контейнеризованными приложениями

### В: Можно ли использовать azd с существующими проектами?
**О**: Да! Вы можете:
1. Использовать `azd init` для добавления конфигурации azd в существующие проекты
2. Адаптировать существующие проекты под структуру шаблонов azd
3. Создавать собственные шаблоны на основе вашей архитектуры

## Аутентификация и доступ

### В: Как пройти аутентификацию в Azure с помощью azd?
**О**: Используйте `azd auth login`, который откроет окно браузера для аутентификации в Azure. Для сценариев CI/CD используйте сервисные принципы или управляемые удостоверения.

### В: Можно ли использовать azd с несколькими подписками Azure?
**О**: Да. Используйте `azd env set AZURE_SUBSCRIPTION_ID <subscription-id>` для указания подписки для каждой среды.

### В: Какие права нужны для развертывания с помощью azd?
**О**: Обычно требуются:
- Роль **Contributor** в группе ресурсов или подписке
- Роль **User Access Administrator**, если развертываются ресурсы, требующие назначений ролей
- Конкретные права зависят от шаблона и развертываемых ресурсов

### В: Можно ли использовать azd в CI/CD пайплайнах?
**О**: Абсолютно! azd разработан для интеграции с CI/CD. Используйте сервисные принципы для аутентификации и задавайте переменные окружения для конфигурации.

### В: Как работать с аутентификацией в GitHub Actions?
**О**: Предпочтительно использовать федерацию удостоверений рабочего процесса (OIDC), настроенную с помощью `azd pipeline config`. Сгенерированный workflow устанавливает AZD и аутентифицирует AZD напрямую с федеративным идентификатором. Один только шаг `azure/login` не выполняет вход в AZD. Шаг входа в существующей задаче выглядит так:
```yaml
permissions:
  contents: read
  id-token: write
steps:
  - uses: actions/checkout@v7
  - uses: Azure/setup-azd@v2
  - run: >-
      azd auth login
      --client-id "${{ vars.AZURE_CLIENT_ID }}"
      --tenant-id "${{ vars.AZURE_TENANT_ID }}"
      --federated-credential-provider github
```

Выполняйте provisioning или развертывание после входа с настроенной средой AZD, подпиской и регионом. Федеративные учетные данные должны доверять репозиторию/референсу workflow или среде GitHub, а роли Azure должны позволять запрашиваемые операции.

## Шаблоны и проекты

### В: Где найти шаблоны azd?
**О**: 
- Официальные и пользовательские шаблоны: [Awesome AZD](https://azure.github.io/awesome-azd/)
- Пользовательские шаблоны: поиск на GitHub по "azd-template"
- Используйте `azd template list` для просмотра доступных шаблонов

### В: Как создать собственный шаблон?
**О**: 
1. Начните с существующей структуры шаблона
2. Измените `azure.yaml`, инфраструктурные файлы и код приложения
3. Тщательно протестируйте с помощью `azd up`
4. Опубликуйте на GitHub с соответствующими тегами

### В: Можно ли использовать azd без шаблона?
**О**: Да, используйте `azd init` в существующем проекте для создания нужных файлов конфигурации. Вам придется вручную настроить `azure.yaml` и инфраструктурные файлы.

### В: В чем разница между официальными и пользовательскими шаблонами?
**О**: 
- **Официальные шаблоны**: Поддерживаются Microsoft, регулярно обновляются, имеют полную документацию
- **Пользовательские шаблоны**: Создаются разработчиками, могут иметь специализированные случаи, качество и поддержка варьируются

### В: Как обновить шаблон в моем проекте?
**О**: Шаблоны не обновляются автоматически. Вы можете:
1. Вручную сравнить и слить изменения из исходного шаблона
2. Начать заново с `azd init` с использованием обновленного шаблона
3. Выбрать отдельные улучшения из обновленных шаблонов

## Развертывание и инфраструктура

### В: Какие сервисы Azure может развертывать azd?
**О**: azd может развертывать любые сервисы Azure через Bicep/ARM шаблоны, включая:
- App Services, Container Apps, Functions
- Базы данных (SQL, PostgreSQL, Cosmos DB)
- Хранилище, Key Vault, Application Insights
- Сети, безопасность и инструменты мониторинга

### В: Можно ли развернуть в нескольких регионах?
**О**: Да, настройте несколько регионов в Bicep шаблонах и указывайте параметр location для каждой среды.

### В: Как обрабатывать миграции схем баз данных?
**О**: Используйте хуки развертывания в `azure.yaml`:
```yaml
hooks:
  postdeploy:
    posix:
      run: ./scripts/migrate-database.sh
    windows:
      run: ./scripts/migrate-database.ps1
```

### В: Можно ли развернуть только инфраструктуру без приложений?
**О**: Да, используйте `azd provision` для развертывания только компонентов инфраструктуры, определенных в шаблонах.

### В: Как развертывать на существующие ресурсы Azure?
**О**: Да, если шаблон это поддерживает. Используйте `existing` в Bicep для ссылок на существующие ресурсы или параметры шаблона для существующих ресурсов и сопоставляйте сервисы приложений с назначенными целями. Это не импортирует право собственности и не создает автоматически отсутствующие разрешения. Перед развертыванием проверьте шаблон.

### В: Можно ли использовать Terraform вместо Bicep?
**О**: Да. AZD поддерживает Terraform, а также Bicep. Выберите шаблон на базе Terraform или настройте `infra.provider: terraform` в `azure.yaml` с соответствующими файлами Terraform и конфигурацией состояния/хранилища. См. [Рабочий процесс Terraform](https://learn.microsoft.com/azure/developer/azure-developer-cli/use-terraform-for-azd).

## Конфигурация и среды

### В: Как управлять различными средами (dev, staging, prod)?
**О**: Создавайте отдельные среды с помощью `azd env new <environment-name>` и настраивайте разные параметры для каждой:
```bash
azd env new development
azd env new staging  
azd env new production
```

### В: Где хранятся конфигурации сред?
**О**: В папке `.azure` внутри каталога вашего проекта. Каждая среда имеет свою папку с файлами конфигурации.

### В: Как установить конфигурацию, специфичную для среды?
**О**: Используйте `azd env set` для настройки переменных окружения:
```bash
azd env set AZURE_LOCATION eastus
azd env set DATABASE_TIER Basic
```

### В: Можно ли делиться конфигурациями сред с членами команды?
**О**: Папка `.azure` содержит конфиденциальную информацию и не должна коммититься в систему контроля версий. Вместо этого:
1. Документируйте необходимые переменные окружения
2. Используйте скрипты развертывания для настройки сред
3. Используйте Azure Key Vault для конфиденциальных данных конфигурации

### В: Как переопределить настройки шаблона по умолчанию?
**О**: Задайте переменные окружения, соответствующие параметрам шаблона:
```bash
azd env set AZURE_LOCATION westus2
azd env set SKU_NAME "B1"
```

Влияют только переменные, используемые шаблоном. `SKU_NAME` выше — пример пользовательского ввода, а не универсальная настройка AZD.

## Устранение неполадок

### В: Почему `azd up` завершается с ошибкой?
**О**: Частые причины:
1. **Проблемы с аутентификацией**: Выполните `azd auth login`
2. **Недостаточные права**: Проверьте назначения ролей Azure
3. **Конфликты в именах ресурсов**: Проверьте конфликтующий ресурс и параметры имен в шаблоне; создайте отдельную среду с помощью `azd env new` для изоляции
4. **Проблемы с квотами/емкостью**: Проверьте доступность в регионе
5. **Ошибки шаблона**: Проверьте Bicep шаблоны на ошибки

### В: Как отлаживать ошибки при развертывании?
**О**: 
1. Используйте `azd deploy --debug` для подробного вывода
2. Проверьте историю развертываний в портале Azure
3. Изучите журнал активности в портале Azure
4. Используйте `azd show` для отображения текущего состояния среды

### В: Почему мои переменные окружения не работают?
**О**: Проверьте:
1. Совпадение имен переменных с параметрами шаблона
2. Правильно ли заключены в кавычки значения с пробелами
3. Выбрана ли нужная среда: `azd env select <environment>`
4. Установлены ли переменные в правильной среде

### В: Как очистить неудачные развертывания?
**О**: 
```bash
azd down
```
Сначала проверьте выбранную среду и подтверждение удаления. Это удалит развернутые ресурсы Azure, но не локальную конфигурацию среды `.azure`. `--purge` также запрашивает окончательное удаление поддерживаемых мягко удаленных ресурсов и может быть заблокирован политиками защиты; это не рутинный шаг восстановления.

### В: Почему после развертывания приложение недоступно?
**О**: Проверьте:
1. Развертывание завершилось успешно
2. Приложение запущено (проверьте логи в портале Azure)
3. Группы безопасности сети пропускают трафик
4. DNS/пользовательские домены настроены правильно

## Затраты и выставление счетов

### В: Сколько будут стоить развертывания azd?
**О**: Стоимость зависит от:
- Развернутых сервисов Azure
- Выбранных уровней/SKU сервисов
- Региональных различий в ценах
- Моделей использования

Используйте [Калькулятор цен Azure](https://azure.microsoft.com/pricing/calculator/) для оценки.

### В: Как контролировать затраты при развертывании azd?
**О**: 
1. Используйте SKU более низких уровней для сред разработки
2. Настройте бюджеты и уведомления Azure
3. Используйте `azd down` для удаления ресурсов, когда они не нужны
4. Выбирайте подходящие регионы (цены варьируются по локациям)
5. Используйте инструменты управления затратами Azure

### В: Есть ли бесплатные уровни для шаблонов azd?
**О**: Некоторые сервисы имеют бесплатные SKU или ежемесячные гранты, в зависимости от права, плана хостинга, региона и ограничений подписки. Это не делает весь шаблон бесплатным: базы данных, поиск, сеть, реестр, телеметрия и инференс моделей могут создавать отдельные расходы. Ознакомьтесь со списком [бесплатных сервисов Azure](https://azure.microsoft.com/free/) и актуальными тарифами для каждого ресурса перед развертыванием.

### В: Как оценить затраты до развертывания?
**О**: 
1. Ознакомьтесь с `main.bicep` шаблона, чтобы увидеть создаваемые ресурсы
2. Используйте Калькулятор цен Azure с конкретными SKU
3. Сначала разверните в среде разработки, чтобы мониторить фактические затраты
4. Используйте Azure Cost Management для детального анализа затрат

## Лучшие практики

### В: Какие лучшие практики для структуры проекта azd?
**О**: 
1. Держите код приложения отдельно от инфраструктуры
2. Используйте осмысленные имена сервисов в `azure.yaml`
3. Внедряйте корректную обработку ошибок в скриптах сборки
4. Используйте конфигурации, специфичные для среды
5. Включайте полную документацию

### В: Как организовать несколько сервисов в azd?
**О**: Используйте рекомендованную структуру:
```
├── src/
│   ├── web/          # Frontend service
│   ├── api/          # Backend service  
│   └── worker/       # Background service
├── infra/            # Infrastructure templates
├── azure.yaml        # azd configuration
└── README.md         # Project documentation
```

### В: Нужно ли коммитить папку `.azure` в систему контроля версий?
**О**: **Нет!** Папка `.azure` содержит конфиденциальную информацию. Добавьте ее в `.gitignore`:
```gitignore
.azure/
```

### В: Как мне обращаться с секретами и конфиденциальной конфигурацией?
**О**: 
1. Используйте Azure Key Vault для хранения секретов
2. Ссылайтесь на секреты Key Vault в конфигурации приложения
3. Никогда не коммитьте секреты в систему контроля версий
4. Используйте управляемые идентичности для аутентификации между сервисами

### В: Какой рекомендуемый подход для CI/CD с azd?
**О**: 
1. Используйте отдельные окружения для каждого этапа (dev/staging/prod)
2. Внедрите автоматическое тестирование перед деплоем
3. Используйте сервисные принципы для аутентификации
4. Храните конфиденциальную конфигурацию в секретах/переменных конвейера
5. Реализуйте ворота одобрения для продакшен-деплоев

## Продвинутые темы

### В: Можно ли расширить azd пользовательской функциональностью?
**О**: Да, с помощью хуков деплоя в `azure.yaml`:
```yaml
hooks:
  predeploy:
    run: ./scripts/custom-setup.sh
  postdeploy:
    run: ./scripts/custom-config.sh
```

### В: Как интегрировать azd с существующими процессами DevOps?
**О**: 
1. Используйте команды azd в существующих скриптах конвейера
2. Стандартизируйте шаблоны azd по командам
3. Интегрируйте с существующим мониторингом и системой оповещений
4. Используйте JSON-вывод azd для интеграции в конвейер

### В: Можно ли использовать azd с Azure DevOps?
**О**: Да, azd работает с любой системой CI/CD. Создавайте Azure DevOps pipeline с командами azd.

### В: Как я могу внести вклад в azd или создать шаблоны сообщества?
**О**: 
1. **azd tool**: Вносите изменения в [Azure/azure-dev](https://github.com/Azure/azure-dev)
2. **Шаблоны**: Следуйте инструкциям для вклада в [Awesome AZD gallery](https://github.com/Azure/awesome-azd#3-contribute-to-gallery)
3. **Документация**: Вносите вклад в документацию [MicrosoftDocs/azure-dev-docs](https://github.com/MicrosoftDocs/azure-dev-docs)

### В: Каковы планы развития azd?
**О**: Ознакомьтесь с [официальным планом развития](https://github.com/Azure/azure-dev/projects) для информации о планируемых функциях и улучшениях.

### В: Как мигрировать с других средств деплоя на azd?
**О**: 
1. Проанализируйте текущую архитектуру деплоя
2. Создайте эквивалентные Bicep шаблоны
3. Настройте `azure.yaml` под текущие сервисы
4. Тщательно протестируйте в среде разработки
