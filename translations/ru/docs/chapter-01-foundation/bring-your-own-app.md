> Цель обзора команд и конфигурации: `azd 1.37.2` (ноябрь 2026). Сгенерированные файлы зависят от обнаруженного приложения; развертывание в Azure не выполнялось в этом обзоре.

## Введение

В [Вашем первом проекте](first-project.md) вы развернули приложение, начиная с шаблона. Но чаще всего у вас уже *есть* приложение — API на Node.js, сервис на Python Flask, веб-приложение .NET — находящееся в папке на вашем компьютере. Этот урок покажет, как добавить azd к существующему коду, чтобы можно было развернуть его с помощью `azd up`, без необходимости шаблона.

## Цели обучения

К концу этого урока вы:
- Поймёте три способа начать проект azd
- Запустите `azd init` внутри существующего кода
- Поймёте, что делают `azure.yaml` и папка `infra/` для вашего приложения
- Узнаете, когда позволить azd генерировать инфраструктуру, а когда писать свою
- Развернёте ваше существующее приложение в Azure с помощью `azd up`

## Результаты обучения

После завершения урока вы сможете:
- Инициализировать azd в уже существующем проекте
- Читать и редактировать базовый файл `azure.yaml`
- Генерировать стартовую инфраструктуру с помощью `azd infra generate`
- Выбирать подходящий хост Azure для вашего приложения
- Развертывать и очищать собственное приложение

## Три способа начать проект azd

| Точка старта | Команда | Когда использовать |
|--------------|----------|------------------|
| **Из шаблона** | `azd init --template <name> .` (пустая директория) | Обучение или начало нового приложения из проверенного примера |
| **Из существующего кода** | `azd init` (в папке проекта) | У вас уже есть приложение и вы хотите его развернуть |
| **Из Git-репозитория** | `azd init --from-code` (в клонированном репозитории) | Внедрение azd для существующего репозитория |

Вы уже практиковались с первым вариантом. Этот урок охватывает второй — самый распространённый сценарий в реальной жизни.

## Шаг 1: Запустите `azd init` в вашем проекте

Откройте терминал **внутри папки вашего существующего проекта** и выполните:

```bash
cd my-existing-app
azd init
```

azd спросит, как вы хотите инициализировать проект. Выберите:

```
? How do you want to initialize your app?
> Use code in the current directory
  Select a template
```

Выберите **"Использовать код в текущей директории."** azd просканирует вашу папку, определит язык и фреймворк и предложит хост.

### Что обнаруживает azd

azd ищет признаки приложения, такие как `package.json`, `requirements.txt`, `pom.xml`, `*.csproj` или `Dockerfile`. Поток инициализации из кода — это не универсальный мастер выбора хоста для каждой поддерживаемой цели развертывания:

| Ваше приложение | Вероятно обнаруженный хост |
|----------------|-------------------------|
| Поддерживаемое веб-приложение Node.js / Python / .NET | Обычно Azure Container Apps; изучите сгенерированное определение |
| Контейнеризованное приложение (`Dockerfile`) | Azure Container Apps |
| Функциональное приложение или проект Static Web Apps | Используйте соответствующий шаблон или создайте `azure.yaml` и инфраструктуру, если инициализация из кода не поддерживает ваш формат |

Подтвердите обнаруженные сервисы, и azd сгенерирует нужные файлы.

## Шаг 2: Понять, что создал azd

После инициализации изучите `azure.yaml`. Поток создания инфраструктуры может держать инфраструктуру неявной до запуска `azd infra generate`; не предполагайте, что `infra/` уже существует:

```
my-existing-app/
├── azure.yaml          # ← NEW: tells azd what to deploy and where
├── infra/              # Materialized with azd infra generate when using implicit infrastructure
│   ├── main.bicep
│   └── main.parameters.json
├── src/ (your code)    # unchanged
└── ...                 # your existing files, untouched
```

### `azure.yaml` — определение проекта

Это сердце проекта azd. Следующее **иллюстративное определение App Service** требует соответствующей инфраструктуры App Service; это не повод менять сгенерированный хост Container Apps без изменения инфраструктуры:

```yaml
# azure.yaml
name: my-existing-app
services:
  web:
    project: ./src           # path to your app code
    language: js             # js | python | dotnet | java
    host: appservice         # appservice | containerapp | function | staticwebapp
```

Блок `services` — ключевая часть: каждая запись сопоставляет папку вашего кода с Azure-хостом. Если в вашем приложении есть и фронтенд, и API, у вас будет два сервиса.

### `infra/` — ваши ресурсы Azure как код

Папка `infra/` содержит Bicep-файлы, которые определяют Azure-ресурсы, необходимые вашему приложению (App Service, база данных и т. д.). Не нужно писать их вручную — azd генерирует рабочую стартовую точку. Вы *можете* редактировать их позже, чтобы добавить ресурсы или повысить безопасность (подробности в [Главе 4](../chapter-04-infrastructure/README.md)).

> **Совет:** Хотите увидеть или настроить сгенерированную инфраструктуру перед развертыванием? Запустите `azd infra generate` (также доступно как `azd infra synth`), чтобы записать инфраструктуру как код на диск и затем просмотреть и управлять версиями.

## Шаг 3: Установите необходимые параметры конфигурации

Если вашему приложению нужны настройки или секреты (строка подключения, API-ключ), не прописывайте их в коде. Используйте переменные окружения:

```bash
# Create an environment
azd env new dev

# Set a non-secret value
azd env set API_VERSION 1.0.0
```

Это хранит только локальное значение. Чтобы повлиять на приложение, явно используйте его в параметрах инфраструктуры, поддерживаемых настройках сервиса или в хуках; установка произвольной переменной не конфигурирует среду выполнения развернутого приложения.

Для настоящих секретов храните их в Key Vault и ссылайтесь на них из инфраструктуры — см. [Главу 3: Конфигурация и аутентификация](../chapter-03-configuration/authsecurity.md).

## Шаг 4: Развертывание

Теперь используйте тот же рабочий процесс, который вы уже знаете:

```bash
# Authenticate (required for azd)
azd auth login

# Preview the resources that will be created
azd provision --preview

# Provision infrastructure and deploy your code
azd up
```

По окончании azd выведет URL вашего приложения. Проверьте его так же, как любое приложение azd:

```bash
azd show           # show endpoints
azd monitor --logs # check logs if needed
```

## Частые проблемы при первом запуске

| Симптом | Вероятная причина | Решение |
|---------|------------------|---------|
| azd не обнаружил моё приложение | Отсутствует манифест (например, `package.json`) | Добавьте манифест или выберите хост вручную во время `azd init` |
| Сборка не проходит во время `azd up` | Приложению нужен шаг сборки | Настройте скрипты пакета приложения или сервисный хук `prepackage`; используйте `dist` для вывода развертывания, а не `buildCommand`/`outputPath` |
| Приложение запускается, но возвращает ошибки | Отсутствует конфигурация/секрет | Подключите значения к настройкам приложения времени выполнения или ссылке Key Vault; одной команды `azd env set` недостаточно |
| Выбран неправильный хост | Автоматическое обнаружение не соответствует вашим требованиям | Измените и `host:`, и соответствующую инфраструктуру, либо выберите подходящий шаблон |

Для дополнительной информации смотрите [Главу 7: Устранение неполадок](../chapter-07-troubleshooting/README.md).

## Очистка

```bash
azd down --force --purge
```

---

## Резюме

- `azd init` → **"Использовать код в текущей директории"** добавляет azd к уже имеющемуся приложению.
- `azure.yaml` сопоставляет папки вашего кода с хостами Azure; `infra/` определяет ресурсы посредством Bicep.
- `azd infra generate` позволяет просматривать или настраивать сгенерированную инфраструктуру.
- После инициализации ваше существующее приложение использует тот же самый рабочий процесс `azd up` / `azd down`, что и приложение на основе шаблона.
